# CLAUDE.md – becauseyoulovejira

Verbindliche Projektregeln. Gilt für jede Änderung in diesem Repo. Bei jeder relevanten Entscheidung aktualisieren.

## 1. Zweck

Privates, lokal laufendes Ticket-Dashboard (Linear-/Jira-artiges Ticket-Handling ohne Prozesslast) für Windows 10, genutzt im Desktop-Browser (Chrome, Firefox, Opera GX). Die komplette Installation ist ein einzelner Ordner (`app/`): Start per Doppelklick, Sicherung und Umzug per Ordnerkopie.

## 3. Tech-Stack (festgelegt – Änderung nur nach Rückfrage beim Nutzer)

- **Backend:** PocketBase **v0.40.4**, Windows-Binary unverändert, kein Go-Build. Datenhaltung SQLite.
  - Serverlogik ausschließlich über JS-Hooks (`app/pb_hooks`, Goja-Runtime, ES5-kompatibel, kein ESM, keine Node-APIs).
  - Schema ausschließlich über handgeschriebene JS-Migrationen (`app/pb_migrations`). Server läuft mit `--automigrate=false`; keine Schemaänderungen über das Admin-Dashboard.
  - Bindung nur an `127.0.0.1` (vorerst; Mehrgeräte geplant, siehe [ADR-0001](docs/adr/0001-betriebsmodell-lokal-mehrgeraete-spaeter.md)), Port 8090. Der Port ist nur in `app/byl-config.json` änderbar (Nutzerwunsch 2026-09-29, [ADR-0039](docs/adr/0039-betriebsskripte.md) §2); die App weicht nie selbst auf einen anderen Port aus.
- **Frontend:** SvelteKit 2 + Svelte 5 + TypeScript (strict), `@sveltejs/adapter-static` im SPA-Modus (`ssr = false`, `prerender = false`, `fallback: 'index.html'`), Build nach `web/build` (Staging), veröffentlicht nach `app/pb_public` durch `scripts/publish-web.mjs` im Root-`npm run build` ([ADR-0040](docs/adr/0040-veroeffentlichen-ohne-unterbrechung.md)). PocketBase JS SDK für API und Realtime.
- **Schriften:** Inter (UI) und JetBrains Mono (Ticket-Keys) lokal über `@fontsource-variable/*`. **Keine externen CDNs** – die App muss offline funktionieren.
- **Geführte Tour:** [driver.js](https://github.com/kamranahmedse/driver.js) `~1.8.0` (Lizenz **MIT**, ohne Abhängigkeiten), npm-Abhängigkeit in `web/package.json`, lokal von Vite gebündelt und erst beim Start der Tour nachgeladen, **kein CDN**. Einzige UI-Bibliothek der App und nur für die Tour (`web/src/lib/tour/`, eigene Styles `lib/styles/tour.css` statt der Standard-CSS); Grenzen in [ADR-0026](docs/adr/0026-einstellungsbereich-und-hinweis-bausteine.md) §8.
- **Editor ([ADR-0032](docs/adr/0032-editor-tiptap-markdown.md), freigegeben vom Nutzer am 2026-09-28):** [Tiptap](https://tiptap.dev) 3 (Kern und die benötigten Extensions, Lizenz **MIT**) mit ProseMirror und `prosemirror-markdown` (MIT) als Brücke auf der markdown-it-Instanz der Anzeige; `@tiptap/markdown` und kostenpflichtige Tiptap-Funktionen werden nicht genutzt. Lokal von Vite gebündelt, erst beim ersten „Bearbeiten“ per `import()` nachgeladen, **kein CDN**, keine Tiptap-Cloud. Tiptap ist headless und keine UI-Bibliothek; Toolbar und Menüs entstehen auf den eigenen Overlay-Bausteinen. Er bearbeitet die Beschreibung in Panel und Vollansicht (seit RT-3), Kommentare, „Neues Ticket“ (auch beim Umwandeln aus dem Eingang) und die Vorlage einer Wiederholung (seit RT-6, [Plan Editor](docs/plan/editor.md)); die `textarea` bleibt als Quelltextmodus „Markdown“ und in Eingang und Erfassen, deren Felder Rohtext bzw. Eingaben für Vorlagen sind. `web/package.json` hält per `overrides` eine einzige markdown-it-Version für Anzeige und Brücke.
- **Browser-Erweiterung für WhatsApp Web ([ADR-0038](docs/adr/0038-eigener-eingang-und-whatsapp-web.md), seit EI-2):** `extensions/whatsapp-web/`, Manifest V3 für Chrome und Edge, ohne Laufzeit-Abhängigkeit und ohne Typpakete für Chrome (`src/chrome.d.ts`). Dev-Abhängigkeiten exakt gepinnt und schon im Repo genutzt (TypeScript, esbuild, Vitest, jsdom, Prettier, ESLint, `@types/node`); esbuild bündelt ohne Minifizierung nach `app/erweiterung-whatsapp-web/`. Liest im offenen Tab nur, sendet nie in WhatsApp, redet nur mit der App auf `127.0.0.1`/`localhost`; alle Selektoren in `src/selectors.ts`, Tests nur mit eigenen, anonymisierten Fixtures (`src/fixtures/`), nie mit web.whatsapp.com.
- **Tests:** Vitest; Hook-Integrationstests per Skript gegen eine Wegwerf-Instanz (temporäres `--dir`). Die Root-Tests liegen unter `tests/unit` und `tests/integration`, die web-Tests unter `web/src/**/*.test.ts`, die Tests der Erweiterung unter `extensions/whatsapp-web/src/**/*.test.ts` (jsdom; `npm test`, `check`, `lint` und `build` im Root schließen sie ein). `npm test` im Root braucht vorher den Web-Build (`app/pb_public`) für den SPA-Fallback-Test; `scripts\build.ps1` hält die Reihenfolge ein (check → lint → build → test) und wird mit `powershell -ExecutionPolicy Bypass -File scripts\build.ps1` aufgerufen.

Zur Laufzeit nur eingebettet im optionalen Mail-Hilfsprozess `app/byl-mail.exe` (Node-24-Single-Executable-Application mit `imapflow` und `postal-mime`, gebündelt mit esbuild, eingespritzt mit postject; [ADR-0016](docs/adr/0016-kanal-architektur-und-mail.md) §4 und §5). Er liest Postfächer nur (IMAP `EXAMINE`, `UID SEARCH`, `BODY.PEEK`, keine Flags, kein SMTP) und schreibt nur über die Ingest-Route mit `BYL_INGEST_TOKEN`. Ein installiertes Node ist für den Betrieb nicht nötig.

### PocketBase-API-Disziplin

Die APIs (Hooks, Migrationen, SDK) haben sich zwischen Versionen stark geändert. Vor jedem Hook-/Migrationscode die Doku der gepinnten Version prüfen (pocketbase.io/docs, JSVM-Referenz pocketbase.io/jsvm) – nicht aus Erinnerung schreiben.
- Hook-Handler müssen `e.next()` aufrufen.
- Create und Update über die Record-API laufen in v0.40.4 **nicht** automatisch in einer Transaktion (nur Delete mit Kaskaden). Hooks, die mehrere Schreibvorgänge atomar brauchen, öffnen sie selbst, und zwar verbindlich über den Helfer `inTransaction(e, fn)` aus `app/pb_hooks/lib/transaction.js` (`fn(txApp)` ruft `e.next()` auf). Ein bloßes `e.app = txApp` ohne Zurücksetzen ist fehlerhaft: Nach dem Commit zeigt `e.app` sonst auf die beendete Transaktion, und die After-Success-Hooks sowie der Realtime-Broadcast scheitern still. Der Helfer setzt `e.app` für die Dauer der Transaktion auf `txApp` und stellt es danach (auch im Fehlerfall) wieder her ([E1-Plan](docs/plan/e1.md) §2, OF-1 und Abschnitt 6, Paket 5).
- In Hooks für DB-Zugriffe `e.app` verwenden, nicht `$app` (Deadlock-Gefahr innerhalb von Transaktionen). In `runInTransaction((txApp) => …)` nur `txApp` verwenden.
- Module per `require(`${__hooks}/lib/<name>.js`)` **innerhalb** des Handlers laden (Handler laufen in isolierten Scopes).
- Filter mit Nutzereingaben immer parametrisiert (`{:param}` bzw. `pb.filter()` im SDK), nie per String-Konkatenation.
- Keine Zeitzonen-APIs der Laufzeit für fachliche Berechnungen: `new Timezone(...)` und `new DateTime(x, "Europe/Berlin")` liefern ohne tzdata stillschweigend UTC ([ADR-0005](docs/adr/0005-zeitzone-europe-berlin.md)).
- **Kein `onServe`:** Die JSVM von 0.40.4 kennt den Hook nicht. Ein Aufruf wirft beim Laden, und die Hook-Datei bricht an dieser Stelle ab. Logik beim Start läuft nach `e.next()` von `onBootstrap`, nur beim Befehl `serve` (`$os.args`) und immer in `try/catch`, denn ein Wurf verhindert den Start. `serve` führt ausstehende Migrationen erst nach `onBootstrap` aus: Beim ersten Start nach einem Update sieht der Handler noch das alte Schema ([ADR-0022](docs/adr/0022-erzeugung-von-instanzen.md), Nachtrag).
- Autodate-Felder: PocketBase liest die Uhr für `created` und `updated` einzeln, sie können um 1 ms abweichen. Wer beide gleich braucht, setzt sie vor dem Speichern mit `record.setRaw` (`record.set` ignoriert Autodate-Felder; Beispiel `newInstance` in `lib/recurrence-service.js`).

## 4. Svelte-5-Runes-Regel (hart)

- Ausschließlich Runes: `$state`, `$derived`, `$effect`, `$props`, `$bindable`.
- Verboten: `export let`, `$:`-Statements, `svelte/store`-Stores für Komponenten- oder App-Zustand, `on:click`-Direktiven, `<slot>`.
- Stattdessen: Event-Attribute (`onclick`), Snippets (`{#snippet}` / `{@render}`), geteilter Zustand in `.svelte.ts`-Modulen mit Runes.
- `$effect` nur für echte Seiteneffekte (Subscriptions, DOM, localStorage), nicht zur Ableitung von Zustand – dafür `$derived`.

- **Historie:** `onRecordUpdate` vergleicht `e.record.original()` feldweise (Whitelist fachlicher Felder) und schreibt in derselben, vom Hook geöffneten Transaktion wie die Änderung nach `ticket_history`; die Anlage wird ebenfalls protokolliert.
- **Parent (Unteraufgaben, [ADR-0033](docs/adr/0033-unteraufgaben.md), umgesetzt mit UA-1 bis UA-5):** genau eine Ebene, im selben Scope, im Hook erzwungen. Erledigen mit offenen Unteraufgaben, die `blocks_parent` tragen, lehnt der Hook mit `validation_parent_open_children` ab, außer mit dem Body-Feld `force` oder `complete_children` (erledigt sie atomar mit). Folgetickets einer Serie haben keinen Parent.
- **Papierkorb ([ADR-0037](docs/adr/0037-papierkorb.md), [Plan Papierkorb](docs/plan/papierkorb.md), seit PB-1, Migration `1790202300_tickets_trash.js`):** Jeder Löschweg ist weich. `lib/trash-service.js` (Regeln rein in `lib/trash-rules.js`) setzt in einer Transaktion `deleted_at`, `deleted_by` und den Schnappschuss `trash` und leert `project`, eigenes `parent`, `recurrence`, `occurrence` sowie bei „Quellen zurück in den Eingang“ `source_item`; Unteraufgaben gehen als Gruppe mit (sie behalten `parent`), eine einzeln gelöschte verlässt ihr übergeordnetes Ticket. Die Route `POST /api/byl/tickets/{id}/delete` antwortet `{ id, updated, tickets }`; `onRecordDeleteRequest` fängt jedes Löschen der Record-API ab (auch den Superuser; ein Ticket, das schon im Papierkorb liegt, löscht er endgültig) und antwortet selbst 204, ohne `e.next()` (das wäre das harte Löschen). Schreibvorgänge des Papierkorbs tragen `@trash_op` (der Update-Hook ruft nur `e.next()`), den Verlauf schreibt der Dienst (Feld `trash`: `trashed`/`restored`, dazu echte Änderungen beim Wiederherstellen). **Unsichtbar** über die API-Regeln (§5 „API-Regeln“); die Hooks lesen über die geleerten Relationen oder prüfen `trashRules.isTrashed` (Ziel einer Verknüpfung, `parent`, „Wiederholen…“, Duplikat-Meldung ohne Key). Nach dem Commit gehen die `delete`-Ereignisse der verborgenen Tickets und Quellen an alle berechtigten Abos (PocketBase meldet verborgene Updates nicht) und das Thema `byl/trash` an die Tabs der Besitzer. **Routen** (nur angemeldet, Sichtbarkeit ohne Papierkorb-Bedingung, vor der Migration 503): `GET /api/byl/trash` (Gruppenanfänge mit Projekt aus dem Schnappschuss, `deleted_by`, Resttagen und der Aufbewahrung), `GET …/{id}` (Vorschau), `POST …/{id}/restore` (`expected_updated`, `project`, `detach_series`), `POST …/{id}/purge`, `POST /api/byl/trash/empty`. **Wiederherstellen** je Gruppe in einer Transaktion, alle Prüfungen vorher: Key bleibt (ohne Projekt oder im selben Projekt mit gleichem Code und Bereich), sonst `validation_trash_project_required` und neue Keys im Zielprojekt; Serie über `reopenConflicts` (`validation_trash_series_conflict`, mit `detach_series` als normales Ticket, `next_due` bleibt); einzeln gelöschte Unteraufgabe zurück an ihr lebendes übergeordnetes Ticket, sonst eigenständig; zurückgegebene Quellen nur, solange sie `new` ohne Ticket sind. **Endgültig** löschen „Endgültig löschen“, „Papierkorb leeren“, der Cron `byl-trash-purge` (täglich 11:45 UTC und beim Start, Berliner Tage nach `users.trash_retention`) und der Rückweg der Migration; verworfene Quellen werden dabei sofort zu geleerten Tombstones (Fingerprint bleibt). Vor dem Neustart löschen alle Wege wie vorher endgültig (`trashReady`).
- **Unterprojekte ([ADR-0034](docs/adr/0034-unterprojekte.md), [Plan Unterprojekte](docs/plan/unterprojekte.md), seit UP-1):** Ein Unterprojekt ist ein Projekt mit `parent` (Migration `1790202100_projects_parent.js`): genau eine Ebene, im selben Scope, mit eigenem Code und Nummernkreis (`GART-3`); Umhängen und Lösen ändern keinen Key. Die Prüfung steht rein in `lib/catalog-rules.js` (`projectParentViolation`, Texte `PROJECT_PARENT_MESSAGES`), der Hook in `lib/catalog-service.js` liest in seiner Transaktion: Selbstbezug, fehlendes oder fremdes Oberprojekt (gleicher Code `validation_project_parent_missing`), zweite Ebene, aktives Projekt unter archiviertem Oberprojekt. Archivieren des Oberprojekts archiviert die aktiven Unterprojekte in derselben Transaktion (`txApp.save`, ihre Hooks laufen, Realtime nach dem Commit); Zurückholen holt sie nicht mit. Ein Projekt mit Unterprojekten lässt sich weder löschen (`validation_project_has_children`) noch in einen anderen Bereich verschieben (`validation_project_scope_children`). Ohne das Feld (vor dem Neustart) verhalten sich die Hooks wie vorher. Unterprojekte sind keine Epics: kein Status, kein Fortschritt, keine Laufzeit. In der SPA (seit UP-2) liefert die Datenschicht `Project.parentId` (ohne das Feld auf dem Server `withoutParentField`, `CatalogStore.hierarchyReady` falsch); der `CatalogStore` löst `parent` auf und hält `activeProjects` in Baum-Reihenfolge; Baum, Pfad „Haus › Garten“, Reihenfolge und Filtermenge rechnet rein `domain/project-tree.ts` (Texte der Codes gleich dem Hook).
- **Eingang ([ADR-0014](docs/adr/0014-datenmodell-eingang.md)):** Alle Kanäle legen Einträge über `app/pb_hooks/lib/inbox-service.js` an. Der Hook setzt `scope`, `fingerprint`, `state = new` und `handled_at`.
  - **Duplikate:** Der Fingerprint ist ein SHA-256 über einen kanalübergreifenden Schlüssel (Message-ID, `UID` plus `RECURRENCE-ID`, Telegram-Kennung, normalisierte URL, …). `UNIQUE (scope, fingerprint)` ist das Sicherheitsnetz, und Duplikate werden als Ergebnis gemeldet, nicht als Fehler.
  - **Umwandeln:** Der Client sendet beim Anlegen nur `source_item`. In derselben Transaktion setzt der Ticket-Hook dann `tickets.source` und den Eintrag auf `converted`. `source_item` bleibt die unveränderliche **Hauptquelle** des Tickets.
  - **Quellen ([ADR-0031](docs/adr/0031-herkunft-sichern.md)):** Die Quellen eines Tickets sind alle Einträge mit `ticket = <id>`; `converted` gilt für Umwandeln und Verknüpfen, die Hauptquelle folgt aus `source_item` (kein Zustand `linked`). Verknüpfen (`new` → `converted` mit Ticket, auch „Dem Ticket zuordnen“), Lösen (`converted` → `new` ohne Ticket) und seit HK-5 Umhängen (`converted` → `converted` mit anderem Ticket, „Anderem Ticket zuordnen …“) laufen über die Record-API; die Hauptquelle lässt sich weder lösen noch umhängen (`validation_inbox_primary_source`, Begründung im Nachtrag der ADR). Der Hook schreibt in derselben Transaktion den Verlaufseintrag `source_link` (JSON mit `item`, `channel`, `title`; beim Verknüpfen `new_value`, beim Lösen `old_value`, beim Umhängen beides: `old_value` mit `moved_to` im alten, `new_value` mit `moved_from` im neuen Ticket). Die SPA lädt das Ticket eines Eintrags per `expand=ticket` mit (`InboxItemSummary.ticket`: Key, Titel, Hauptquelle). Quellen sind nicht löschbar: `deleteRule` mit `ticket = ""` (Migration `1790201800_inbox_items_delete_guard.js`) und `onRecordDeleteRequest` für Einträge mit Ticket oder als Hauptquelle (`validation_inbox_item_linked`).
  - **Ticket löschen (seit HK-6, ADR-0031 Nachtrag B; seit PB-1 nur noch das endgültige Löschen, das normale Löschen verschiebt in den Papierkorb, siehe unten):** Quellen werden nie mitgelöscht und nie als `converted` ohne Ticket zurückgelassen. `onRecordDelete` von `tickets` merkt sich die Quellen vor `e.next()` und setzt sie danach in derselben Transaktion auf `new` (Standard jedes Löschwegs) oder `discarded` (Tombstone), mit `ticket` leer und `source_meta.ticket_deleted = { key, at }` (Hinweis im Panel; beim erneuten Verknüpfen entfernt). Die Wahl kommt über `POST /api/byl/tickets/{id}/delete` mit `{ sources: "inbox" | "discard" }` (deleteRule, sonst 404; flüchtiger Schlüssel `@source_handling`). Die Migration `1790201900_inbox_items_orphans.js` stellt verwaiste Einträge von vorher einmalig auf `new` (per `UPDATE`, mit `restore` für den Rollback).
  - **Seitenkopie ([ADR-0031](docs/adr/0031-herkunft-sichern.md) §6):** `POST /api/byl/inbox/{id}/page` (angemeldet, nur sichtbare Link-Einträge mit `source_url`, einmal, sonst 409) ruft die Adresse per `$http.send` ab (GET, 10 s, `Range` bis 2 MB, nur 200/206 mit HTML). Vorher prüft `lib/url-guard.js` (rein): nur http(s), keine Anmeldedaten, Ports 80/443/8080/8443, IP-Literale in jeder Schreibweise (inet_aton, IPv6 mit eingebettetem IPv4) gegen private, Loopback-, Link-Local-, Metadaten- und reservierte Bereiche, Namen ohne Punkt, lokale Endungen und Dienste wie `nip.io`. Grenzen der JSVM (keine DNS-Auflösung, Weiterleitungen folgt `$http.send` selbst, Größe erst nach dem Laden) stehen in der ADR. Gespeichert werden der Text (`lib/html-text.js`, ES5-Kopie von `htmlToText` mit Paritätstest) unter dem Auszug in `body`, die HTML-Datei (höchstens 2 MB, UTF-8 bzw. Windows-1252 gelesen, `lib/page-copy.js`) als `original` und `source_meta.page` (`fetched_at`, `size`, `truncated`, `charset`, `title`). Nur Tests setzen `BYL_TEST_PAGE_PORT`, das genau `127.0.0.1:<Port>` für einen Fake-Server freigibt.
  - **Verworfen ist ein Tombstone:** Nach 30 vollen Berliner Tagen leert der tägliche Cron-Job `byl-inbox-cleanup` Text, Originaldatei und `source_meta` (bis auf `keyword`, `all_day`, `recurrence_id`) und kürzt den Titel. Fingerprint und Zustand bleiben.
  - **Quelldatum:** `source_date` wird nie automatisch zur Fälligkeit.
- **„Neu“ ([ADR-0015](docs/adr/0015-neu-markierung-pro-nutzer.md)):** Ein Ticket ist für einen Nutzer neu, wenn `created >= users.unread_since` (leer = `created` des Nutzers), der Status nicht `done` ist und es keine Zeile in `ticket_reads` gibt. Öffnen und einzelnes Anlegen markieren gelesen.
- **Kanäle und Stichwörter ([ADR-0016](docs/adr/0016-kanal-architektur-und-mail.md), [ADR-0020](docs/adr/0020-stichwoerter-pro-kanal.md)):** Zugangsdaten stehen nur als `BYL_*`-Variablen im Windows-Konto; `connections.secret_env` nennt den Namen ([ADR-0018](docs/adr/0018-secrets.md)).
  - Automatisch übernommen wird nur, was ein Stichwort der Verbindung trifft. Der Abgleich läuft zweimal rein und gleich (`lib/keywords.js`, `domain/keywords.ts`, Paritätstest). Bei Mail (Postfach, Postfach-Auswahl, `.eml`) werden Betreff und Absender (`source_meta.from`, Konstante `MAIL_MATCH_FROM`) durchsucht, mit `match_body` zusätzlich die Kopfzeilen To, Cc, Reply-To, Sender, List-Id, Organization und der ganze Text samt HTML-Teil (`mailMatchTexts`, je Teil bis `MAIL_TEXT_MAX_CHARS`; [ADR-0020](docs/adr/0020-stichwoerter-pro-kanal.md), Nachtrag 2); die Ingest-Route prüft das mit `match_texts` nach.
  - Postfächer: Durchsucht wird der **gesamte Posteingang** (nie Papierkorb, Spam, Gesendet oder andere Ordner), beim ersten Abruf, nach jeder Änderung der Stichwörter oder von `match_body` (Standard an), nach neuer `UIDVALIDITY` und auf Knopfdruck; danach neue Mails über den Cursor. Blöcke zu 500 Mails von neu nach alt, Fortschritt in `connections.scan`, abbrechbar, höchstens 200 neue Einträge je Lauf (dann „Weitere Treffer – erneut abrufen“). Kopfzeilen prüft der Hilfsprozess lokal, den Text über `UID SEARCH` des Servers mit Rückfall auf Laden der Mails; geladen und genau geprüft werden nur Kandidaten ([ADR-0020](docs/adr/0020-stichwoerter-pro-kanal.md), Nachtrag 3).
  - **Originaldateien bis 25 MB** (seit HK-8, ADR-0031 Nachtrag D: `MAIL_MAX_MB`/`MAIL_MAX_BYTES` in `domain/inbox-mail.ts` für SPA und Hilfsprozess, `inbox_items.original.maxSize` per Migration `1790202000_inbox_items_original_size.js`, Body-Limit der Ingest-Route 27 MB, `byl-mail.exe` 0.9.0; vorher 10 MB). **Mails über der Grenze** (`MAIL_MAX_BYTES`) kommen seit `byl-mail.exe` 0.8.0 ohne Originaldatei: gelesen werden nur die ersten 2 MB (`MAIL_PARTIAL_BYTES`, `BODY.PEEK[]<0.n>`, sonst nur der Kopf), mit `source_meta.original_omitted = "too_large"` und `original_size` und dem Hinweis `ORIGINAL_OMITTED_NOTE` am Ende des Textes (`mailToDraft(…, { omittedSize })`), beim Abruf, bei der Vollsuche, in der Postfach-Auswahl und für `.eml`-Dateien. Die Ingest-Route prüft beide Schlüssel ([ADR-0031](docs/adr/0031-herkunft-sichern.md) §4).
  - Datei-Importe und die Postfach-Auswahl sind manuell und gehen auch ohne Stichwort.
  - **Eigener Eingang ([ADR-0038](docs/adr/0038-eigener-eingang-und-whatsapp-web.md), [Plan](docs/plan/eigener-eingang-whatsapp-web.md), seit EI-1, Migration `1790202400_inbox_keys.js`):** `app/pb_hooks/inbox-keys.pb.js` mit `lib/inbox-key-service.js` und den reinen Regeln `lib/inbox-key-rules.js`. `POST /api/byl/inbox/keys` (angemeldet) legt einen Zugangsschlüssel `byl_` plus 40 Zeichen an und zeigt ihn einmal; gespeichert werden nur SHA-256 und Anfang. Liste und Widerruf über die Record-API von `inbox_keys`. `POST /api/byl/inbox/ingest` (nur `Authorization: Bearer`, Body bis 512 KB) legt einen privaten Eintrag des Besitzers an: `channel` `api` (Standard) oder `whatsapp-web`, `mode` `manual` (immer) oder `auto` (nur mit Stichwort des Kanals in Titel oder Text, sonst 422 `filtered`), `text`, `external_id` (Fingerprint `<channel>|<external_id>`, Duplikat 200 samt Tombstone), `title?`, `url?`, `sender?`, `chat?`, `sent_at?` (ISO mit Zone → `source_date`). `GET` derselben Adresse ist „Verbindung testen“. Keine Schlüssel oder Inhalte in Logs. Familie: `api` „Manuell“, `whatsapp-web` „Chat“.
  - Google Calendar und Telegram laufen per Cron im Hook (`lib/channel-runner.js`). Postfächer (Web.de, Gmail) holt `byl-mail.exe` über die Ingest-Route mit `BYL_INGEST_TOKEN`.

### Scopes und Nummernkreise

- Jeder Datensatz gehört genau einem Scope: privat `u:<ownerId>` (household leer) oder Haushalt `h:<householdId>`. Der Hook setzt das Feld `scope` auf `projects`, `tags`, `tickets`, `inbox_items`, `connections` und `recurrence_rules`.
- Key: `<CODE>-<NR>` mit Projekt, sonst `TASK-<NR>`. Nummernkreise je Scope + Projekt bzw. Scope + TASK (Zählerschlüssel `<scope>:<projectId|TASK>`).
- Vergabe im `onRecordCreate`-Hook innerhalb einer vom Hook geöffneten Transaktion (siehe §3): UPSERT `INSERT … ON CONFLICT(key) DO UPDATE SET value = value + 1 RETURNING value` auf `ticket_counters` (legt fehlende Zähler an, Schreib-Lock sofort, robust gegen gleichzeitige Anlage; OF-1). Eindeutige Indizes `tickets(scope, key)`, `projects(scope, code)` und `tags(scope, name COLLATE NOCASE)` als Sicherheitsnetz.
- Wechsel von Projekt oder Scope ⇒ neuer Key im Ziel-Nummernkreis; alter Key bleibt in der Historie. URLs referenzieren Tickets per Record-ID, nie per Key.

## 6. Wiederkehrende Aufgaben (Kernfunktion)

- Prinzip Vorlage/Instanz: Eine Regel erzeugt Tickets. **Pro Regel standardmäßig maximal eine offene Instanz** (Status ≠ done); Erzeugung ist idempotent. Seit OR-5 (Nutzerentscheidung 2026-09-28, [ADR-0022](docs/adr/0022-erzeugung-von-instanzen.md) Nachtrag 2) kann eine Regel mit festem Rhythmus stattdessen **„Jeden Termin einzeln anlegen“** (`each_occurrence`, Switch pro Regel, standardmäßig aus): Jeder Termin bekommt ein eigenes Ticket, auch wenn frühere noch offen sind, jeder Termin höchstens einmal.
- `calendar`: selbst implementierte RRULE-Teilmenge – täglich, wöchentlich (mit Wochentagen), monatlich (Tag des Monats oder letzter Tag), jährlich, jeweils mit Intervall.
- `after_completion`: nächste Fälligkeit = Erledigungsdatum + Intervall.
- Auslöser: Erledigen der aktuellen Instanz (Hook), Cron-Hook für Kalenderregeln, Catch-up beim Serverstart. Verpasste Termine ⇒ genau **eine** Instanz mit dem jüngsten fälligen Termin, keine Stapel; sie trägt den Verlaufseintrag `recurrence_skipped` mit Zahl und Daten der übersprungenen Termine, den Verlauf und Zeile „Wiederholt sich“ neutral nennen ([ADR-0022](docs/adr/0022-erzeugung-von-instanzen.md) Nachtrag 4); mit „Jeden Termin einzeln anlegen“ ein Ticket je verpasstem Termin, höchstens `EACH_MAX_PER_RUN` = 20 je Regel und Lauf (der Rest im nächsten Lauf, bis dahin ein neutraler `last_hint`). Liegen dabei **mehr als 20 Termine vor heute** ohne Ticket, legt die Regel nichts an und wartet auf eine Entscheidung (`last_hint` = `CATCH_UP_ASK_HINT`, kein Feld, keine Migration): Body-Feld `backlog` `all` („Alle N nachholen“, dann Stapel zu 20 mit `CATCH_UP_ALL_HINT`) oder `today` („Nur ab heute“, `next_due` auf den ersten Termin ab heute); anderes lehnt der Hook mit `validation_recurrence_backlog` ab ([ADR-0022](docs/adr/0022-erzeugung-von-instanzen.md) Nachtrag 5).
- Berechnung in `app/pb_hooks/lib/recurrence.js`: rein, seiteneffektfrei, CommonJS, ES5, ohne Abhängigkeiten; rechnet nur mit Kalenderdaten, „heute" wird als Parameter übergeben. Vitest-Pflichtfälle: Monatsenden, Schaltjahre, Sommerzeit, lange Ausfallzeiten.
- Umsetzung seit E5 ([ADR-0021](docs/adr/0021-regelmodell-wiederkehrende-aufgaben.md) bis [ADR-0024](docs/adr/0024-serien-aus-kalendern.md), jeweils mit Nachtrag; [E5-Plan](docs/plan/e5.md)):
  - **Rechnen:** `lib/recurrence.js` hat den Spiegel `web/src/lib/domain/recurrence.ts`. Eine gemeinsame Falltabelle (`tests/fixtures/recurrence/cases.json`) und ein Paritätstest mit Zufallsregeln halten beide gleich. Monatstage 29 bis 31 werden am Monatsende geklemmt, der 29.02. jährlich im Nicht-Schaltjahr auf den 28.02. Kein Hook und keine Komponente rechnet selbst mit Tagen, Wochen oder Monaten.
  - **Erzeugen:** `lib/recurrence-service.js` (`materialize` je Regel in einer Transaktion, `runDue` für alle fälligen). Ein eindeutiger Teilindex sichert die Invariante zusätzlich ab, seit OR-5 (Migration `1790202200_recurrence_each_occurrence.js`) `tickets (recurrence, occurrence) WHERE recurrence != '' AND status != 'done'`, seit PB-1 (Migration `1790202300_tickets_trash.js`) mit `AND deleted_at = ''` (Tickets im Papierkorb blockieren nie): `occurrence` (Datum der Serie) setzt nur der Erzeugungsdienst und nur mit „Jeden Termin einzeln anlegen“, sonst ist es leer, so bleibt ohne Schalter eine offene Instanz je Regel und mit Schalter eine je Termin; der Dienst prüft beides zusätzlich in seiner Transaktion. Ein Verstoß zählt als „schon vorhanden“. Der Rückweg der Migration lässt bei mehreren offenen Tickets einer Regel nur das jüngste in der Serie. Cron `byl-recurrence` läuft stündlich (`7 * * * *`, UTC, also auch in Berliner Zeit um xx:07; der erste Lauf eines Tages gegen 00:07), der Start nach `e.next()` von `onBootstrap` (siehe §3, kein `onServe`) holt fällige Regeln und die Bereinigung des Eingangs nach. Start und Cron werfen nie; Fehler gehen bereinigt ins Log und als neutraler `last_hint` an die Regel.
  - **Vorlauf:** Das nächste Ticket entsteht `lead_days` Tage vor seiner Fälligkeit (Standard 3, 0 bis 30, OF-E5-1). Bei `after_completion` steht der Folgetermin atomar mit dem Erledigen fest (Berliner „heute“ im Moment des Erledigens), das Ticket entsteht nach dem Commit, notfalls per Cron. Erzeugte Tickets protokollieren die Anlage ohne Nutzer mit der Regel als `old_value` („Wiederholung“ als Urheber).
  - **Rückgängig:** Wird eine Instanz wieder geöffnet, löscht der Hook ein unberührtes Folgeticket und stellt `next_due` wieder her, aber nur, wenn sie der **direkte Vorgänger** ist (die zuletzt erledigte Instanz der Regel); eine ältere lehnt er mit `validation_recurrence_reopen_older` und dem Key des offenen Tickets ab ([ADR-0023](docs/adr/0023-lebenszyklus-von-regeln-und-instanzen.md) Nachtrag 4). Unberührt heißt: nicht vor dem `completed_at` entstanden, `updated = created` und ohne Kommentare. Ist das Folgeticket schon bearbeitet, lehnt der Hook das Wiedereröffnen mit `validation_recurrence_open_instance` und dem Key ab. Bei beiden Ablehnungen bietet die Oberfläche „Als normales Ticket wieder öffnen (aus der Serie lösen)“ an (Status und `recurrence: ""` in einer Anfrage; inline unter dem Status bzw. als Aktion des Fehler-Flags der Tabelle). Mit „Jeden Termin einzeln anlegen“ steht nur ein offenes Ticket desselben Termins entgegen (im Normalfall keines): Wiedereröffnen geht dann frei, nichts wird gelöscht, `next_due` bleibt ([ADR-0023](docs/adr/0023-lebenszyklus-von-regeln-und-instanzen.md) Nachtrag 2).
  - **Pausieren und Fortsetzen:** Pausieren erzeugt nichts mehr; die offene Instanz bleibt ein normales Ticket. Fortsetzen holt die Pause nicht nach. Ein archiviertes Projekt der Vorlage pausiert die Regel mit neutralem Hinweis; Fortsetzen geht erst mit aktivem oder anderem Projekt. Die Vorlage zu ändern wirkt nur auf künftige Tickets, ein neuer Rhythmus rechnet `next_due` neu.
  - **Löschen und Lösen:** Das Löschen der offenen Instanz oder „Aus der Serie lösen“ überspringt bei `calendar` den Termin; bei `after_completion` wird `next_due` heute + Intervall. Ein Ersatz entsteht nicht im selben Schritt: Liegt der nächste Termin schon im Vorlauf, entsteht sein Ticket beim nächsten stündlichen Lauf (xx:07 Berliner Zeit) oder Start ([ADR-0023](docs/adr/0023-lebenszyklus-von-regeln-und-instanzen.md) Nachtrag 5). Das Löschen einer Regel lässt alle Tickets stehen (OF-E5-4); die Historie zeigt „Wiederholung entfernt“. Seit PB-1 verschiebt das Löschen die Instanz in den Papierkorb (dieselbe Wirkung auf die Regel; die Instanz verliert `recurrence` und `occurrence`, der Schnappschuss hält beide); der Cron erzeugt die nächste zum nächsten Termin wie nach dem Hartlöschen. Wiederherstellen prüft in der Transaktion mit `reopenConflicts` gegen lebende offene Tickets der Serie, verdoppelt nie (`validation_trash_series_conflict`, mit `detach_series` als normales Ticket) und lässt `next_due` stehen ([ADR-0023](docs/adr/0023-lebenszyklus-von-regeln-und-instanzen.md) Nachtrag 3).
  - **Vorschläge aus Kalenderserien:** `web/src/lib/domain/rrule.ts` (nur SPA, streng) bildet die `RRULE` von `.ics`- und Google-Calendar-Serien auf die Teilmenge ab, sonst gibt es einen neutralen Hinweis mit Grund und nie einen Teilvorschlag. Serien mit `UNTIL` oder `COUNT` bekommen nur den Hinweis (OF-E5-5). Eine Regel entsteht nur nach Klick („Als Wiederholung übernehmen“, P-5), in zwei Schritten: erst das Ticket, dann die Regel mit dem Ticket als Instanz. Scheitert die Regel, bleibt das Ticket.
  - **Vor der Migration** (Instanz noch ohne Neustart) verhalten sich alle Hooks wie in E4 (`schemaReady`), und die SPA zeigt neutral „… nach dem nächsten Neustart verfügbar“ mit `neu-starten.bat` (seit BS-3). Ebenso vor der Migration von OR-5 (`eachReady`): eine offene Instanz je Regel wie bisher, ein gesendetes `each_occurrence` wird ignoriert, und die SPA zeigt den Switch erst, wenn ein Filter auf `each_occurrence` nicht mehr mit 400 antwortet (`RecurrenceStore.eachReady`).

- Seitenaufbau ab E3 nach dem Vorbild des Task-Boards, mit eigenen Farben und eigenem Code ([ADR-0010](docs/adr/0010-layout-nach-task-board.md)); was Client und Server bei Filter, Suche und Sortierung rechnen: [ADR-0013](docs/adr/0013-filter-suche-sortierung-gruppierung.md).
- Ansicht „Aufgaben“ ([ADR-0010](docs/adr/0010-layout-nach-task-board.md)): Kopfzeile (App-Name als Link auf „Aufgaben“ mit Zähler der nicht erledigten Tickets, Bereichs-Umschalter, „Neues Ticket“, Hilfe-Menü „?“ seit EH-9, Zahnrad „Einstellungen“ seit EH-1, Theme-Umschalter „Darstellung“, Sitzung), Abschnittsleiste (Umschalter „Aufgaben | Projekte | Eingang | Wiederholungen“ mit Zahlen für „neu“, „Erledigte anzeigen“, „Gruppieren“, seit SP-3 „Spalten“), Kennzahlen-Kacheln, Filterleiste mit Suche, dann die Tabelle mit sortierbaren Spaltenköpfen und Gruppen (Key mit Punkt für „neu“, Priorität, Status-Pille, Titel mit Symbol der Quelle und Icon für wiederkehrend, Quelle (standardmäßig aus), Projekt, Tags, Fälligkeit relativ, Erstellt, Aktionen mit Häkchen; seit UA-5 der Chip „2/5“ am übergeordneten Ticket und eingerückte Unteraufgaben nach [ADR-0033](docs/adr/0033-unteraufgaben.md) §5; ein Icon für „blockiert“ kommt erst mit den Abhängigkeiten, Stufe 2) und rechts das Detail-Panel. Unteraufgaben (Abschnitt in Panel und Vollansicht, Zeile „Übergeordnet“, Frage beim Erledigen) beschreibt [ADR-0033](docs/adr/0033-unteraufgaben.md) §4. Das Menü „Spalten“ ([ADR-0030](docs/adr/0030-spalten-breiten-und-kompakte-zeilen.md) §4, Popover der Art `panel`) blendet die optionalen Spalten per Checkbox ein und aus, ändert ihre Breite mit „schmaler“/„breiter“ um 1rem (Ansage per `aria-live`, Tastaturweg zum Griff) und setzt mit „Standard wiederherstellen“ die Tabelle ohne Rückfrage zurück (Info-Flag „Spalten zurückgesetzt“); wegen Platz ausgeblendete Spalten bleiben angehakt mit dem Hinweis „wegen Platz ausgeblendet“. Auswahl (seit BI-2), Key, Titel und Häkchen sind immer sichtbar. Kompakte Zeilen (seit SP-4, ADR-0030 §6): Der Titel hat höchstens 2 Zeilen (`line-clamp`, nur optisch; `title` ab 60 Zeichen), die Tags stehen einzeilig; wie viele Chips passen, rechnet `fitChips` mit `measureText` einer `OffscreenCanvas` (ohne Canvas geschätzt), der Rest steht als nicht interaktives „+N“ mit `title` „Weitere Tags: …“ und die ganze Liste als verborgener Text für Screenreader. Die Projektansicht `/projekte` ersetzt Kennzahlen, Filterleiste und Tabelle durch die Projektliste (`ProjectTable`, Standard: Code in Mono, Name als Link aufs Projekt-Panel, aktiv, gesamt, neu, archiviert, sortierbar) oder wahlweise die Projektkacheln; Umschalter als Symbolpaar mit `aria-pressed` in der Abschnittsleiste, dazu Suche nach Name oder Code und „Archivierte anzeigen“. Darstellung, Sortierung, Suche und Schalter stehen in der URL (`darstellung`, `sort`, `q`, `archiviert`), die Darstellung zusätzlich in `localStorage` `byl-projects-view`. Unterprojekte ([ADR-0034](docs/adr/0034-unterprojekte.md), seit UP-3) stehen in Liste und Kacheln als Baum unter ihrem Oberprojekt, in derselben Sortierung (`projectRows`): in der Liste eingerückt in der Namenszelle (die Spalten bleiben nach ADR-0030) mit dem Disclosure-Knopf „Unterprojekte von Haus“ (`aria-expanded`), in den Kacheln als eingerücktes Raster mit „in Haus“ und dem Knopf „3 Unterprojekte“; zugeklappt wird je Tab (`sessionStorage` `byl-projects-collapsed`), eine Suche zeigt passende Unterprojekte mit ihrem Oberprojekt als Kontext. Das Projekt-Panel (seit UP-4) hat das Feld „Oberprojekt“ (natives `select`, „Keins“ und die aktiven obersten Projekte; gesperrt bei einem Projekt mit Unterprojekten; vor dem Neustart der Hinweis `restartNeeded`), bei obersten Projekten den Abschnitt „Unterprojekte“ mit „Unterprojekt anlegen“ (`/projekte/neu?oberprojekt=<id>`), bei Unterprojekten die Brotkrumen „Projekte › Haus › Garten“; Archivieren mit aktiven Unterprojekten fragt mit ihrer Zahl, ein Unterprojekt unter archiviertem Oberprojekt kommt über „Mit Oberprojekt zurückholen“ zurück, und Löschen gibt es nur ohne Tickets und Unterprojekte. Die Zahlen eines Oberprojekts (aktiv, gesamt, neu; seit UP-6) zählen seine Unterprojekte mit, auch archivierte (`aggregateCounts`, ohne neue Serveranfrage), mit „inkl. Unterprojekte“ als `title` und für Screenreader; das Panel nennt „davon direkt in Haus“, und ob der Code fest ist, entscheiden die eigenen Tickets. Die Tag-Verwaltung steht seit dem Nutzerwunsch nach EH-4 unter „Einstellungen → Tags“.
- Filter (Status, Projekt, Tag, Priorität, Fälligkeit, Quelle, seit OR-2 „Wiederkehrend“ mit `wiederholung=wiederkehrend|einmalig`, Server `recurrence != ""` mit Paritätstest), Sortierung, Gruppierung (auch „Nach Quelle“ und „Nach Wiederholung“; seit OR-3 über höchstens zwei Ebenen mit `untergruppe`, aufklappbare Gruppenköpfe mit Zählern, zugeklappt je Tab in `sessionStorage` `byl-groups-collapsed`, Einrückung von Unteraufgaben nur in derselben Blattgruppe, [ADR-0013](docs/adr/0013-filter-suche-sortierung-gruppierung.md) Nachtrag B), Suche (PocketBase-Filter auf Titel und Beschreibung); Filterzustand in der URL. Quelle als Familien ([ADR-0019](docs/adr/0019-kanal-filter-und-gruppierung.md)); die eigene Spalte „Quelle“ gibt es seit SP-3 über das Menü „Spalten“. Unterprojekte (seit UP-5, [ADR-0034](docs/adr/0034-unterprojekte.md) §6): Der Filter „Projekt“ schließt sie standardmäßig ein (auch archivierte), `unterprojekte=0` schließt sie aus (Checkbox „Unterprojekte einbeziehen“ im Popover, gesperrt ohne Unterprojekte); Client (`matchesFilter` mit `subProjectsOf` des Katalogs) und Server (`project = p || project.parent = p` nur, wenn der Katalog Unterprojekte kennt) rechnen gleich (Paritätstest). Auswahllisten und Filter nennen Unterprojekte „Haus › Garten (GART)“ in Baum-Reihenfolge, die Spalte „Projekt“ zeigt „Haus › Garten“, die Sortierung „Projekt“ folgt dem Pfad, „Nach Projekt“ gruppiert je Projekt mit dem Pfad als Titel, und der Pfad im Kopf eines Tickets beginnt mit „Haus › Garten“. Unteraufgaben übernehmen das Projekt ihres übergeordneten Tickets 1:1.

- **Quellen eines Tickets ([ADR-0031](docs/adr/0031-herkunft-sichern.md), seit HK-2):** Abschnitt „Quellen“ (`TicketSources`) im Panel nach Quelle und Daten, in der Vollansicht zwischen Beschreibung und Aktivität: je verknüpftem Eintrag Kanal, Quelldatum bzw. Eingang, Absender bzw. Chat bzw. Adresse, „Hauptquelle“ und der Kopie-Status als `Lozenge` (`copyCompleteness` in `domain/sources.ts`: „Vollständig“, „Nur Text“, „Nur Adresse“, „Ohne Originaldatei (zu groß)“), dazu „Ansehen“ und die Symbolknöpfe „Originaldatei … herunterladen“, „… anderem Ticket zuordnen …“ und „… lösen“ (die beiden letzten nie bei der Hauptquelle; sie sagt stattdessen, warum sie bleibt). Das Panel eines umgewandelten oder verknüpften Eintrags zeigt oben den Block „Gehört zu HAUS-12 · Titel“ (Akzentfläche mit Rand) mit „Ticket öffnen“, „Anderem Ticket zuordnen …“ und „Lösen“ bzw. bei der Hauptquelle dem Grund; „Anderem Ticket zuordnen …“ öffnet `MoveSourceDialog` (Modal M, Ticketsuche ohne das aktuelle Ticket, seit HK-5). „Quelle hinzufügen …“ öffnet ein Modal M mit Suche und Checkboxen über die neuen Einträge. Im Eingang verknüpft „Mit Ticket verknüpfen …“ (Panel eines neuen Eintrags und Auswahlleiste) über `LinkTicketDialog` (Modal M) mit der Ticketsuche `TicketCombobox` (APG-Combobox, Liste im Fluss des Modals, Suche nach Nummer, Key oder Titel über `searchTickets`, auch erledigte). Alle Wege laufen über den `TicketSourcesStore` im `(app)`-Layout (eigenes Realtime-Abo auf `inbox_items`, gibt Änderungen sofort an den `InboxStore`); je Eintrag einzeln, Teilfehler bleiben mit Grund stehen, ein Flag nennt das Ergebnis. Das Panel eines Eintrags zeigt die Zeile „Kopie“ und bei unvollständiger Kopie eine neutrale `SectionMessage`; bei einem Web-Link ohne Seitenkopie trägt sie „Seiteninhalt sichern“ (`InboxStore.savePage`, danach wird der Text neu geladen, Zeile „Seite gesichert“ mit Zeitpunkt). In der Vorlage „Web-Link“ (Bookmarklet) steht die Checkbox „Seiteninhalt sichern“, standardmäßig an; die Seite wird nach dem Speichern des Eintrags abgerufen, ihr Ergebnis steht in der Meldung des Formulars.
- **Overlays und Rückmeldungen ([ADR-0025](docs/adr/0025-ui-konsistenz-overlay-system.md), Umsetzung in Paketen UI-1 bis UI-9 nach [docs/plan/e6-ui.md](docs/plan/e6-ui.md)):**
  - Genau sechs Bausteine unter `web/src/lib/components/overlay/` (Logik in `web/src/lib/overlay/`): Modal, Bestätigung, Popover, Seitenpanel, Vollansicht, Flag. Kein `window.confirm`, keine eigenen Dropdowns, kein eigenes `<dialog>` und kein eigener `::backdrop` in Komponenten, keine UI-Bibliothek.
  - **Modal:** Größen S/M/L/XL (400/600/800/1000 px), fester Kopf mit Titel und ×, scrollender Inhalt, fester Fuß rechtsbündig (sekundär links von primär; „Abbrechen“, solange nichts gespeichert ist, sonst „Schließen“). ×, Esc und Klick aufs Blanket schließen; bei ungespeicherten Eingaben ersetzt eine Verwerfen-Frage den Fuß, bei laufender Aktion ist jeder Weg gesperrt. Fokus beim Öffnen auf das erste Element des Inhalts, beim Schließen zurück zum Auslöser, beides im Baustein. Kein Dialog aus einem Dialog.
  - **Bestätigung:** Modal S, Titel als Frage, Knopf mit Verb, erster Fokus auf „Abbrechen“, nicht rot. Navigation mit ungespeicherten Eingaben fragt über diesen Dialog (`beforeNavigate` bricht ab und navigiert nach „Verwerfen“ erneut), aus der Vollansicht inline (siehe dort).
  - **Popover:** `popover="auto"` mit JS-Positionierung (unter dem Knopf, 4 px Abstand, Flip, Klemmen am Rand), Arten `menu` und `panel`; `aria-haspopup`, `aria-expanded`, `aria-controls`; Esc und Klick daneben schließen, der Fokus kehrt zum Knopf zurück. Seit UI-9 sind auch die Filter „Projekt“ und „Tag“ Popover (`FilterPopover`, Art `panel` mit Radios, Suchfeld ab 10 Einträgen), und die Vorschlagsliste des `TagPicker` liegt als `popover="manual"` im Top-Layer (per `place()` unter dem Feld, Esc verbraucht sie per `preventDefault`); seit RT-4 ist sie der Baustein `SuggestionList`, den auch das „/“-Menü des Editors nutzt. Popover kennen seit RT-4 `open()` (Öffnen per Code, etwa Strg+K), `onopen` und `returnFocus` (Fokus nach dem Schließen zurück in den Text statt auf den Knopf). Native `<select>` bleiben in Formularen.
  - **Tag-Eingabe** (Nutzerwunsch, [Plan Spalten](docs/plan/e6-spalten.md) „Tags“; überall, wo der `TagPicker` steht: Panel, Vollansicht, „Neues Ticket“, Sammelumwandeln, Erfassen, Regel): Ein Komma übernimmt den Text vor der Schreibmarke als Tag, Enter den markierten Vorschlag oder sonst den Text, und das Feld leert sich. Eine eingefügte Liste mit Kommas oder Zeilenumbrüchen wird zu mehreren Tags. Die Rücktaste im leeren Feld entfernt den letzten Tag und holt seinen Namen als bearbeitbaren Text zurück; weitere Rücktasten löschen normal. Bestehende Tags werden ohne Groß-/Kleinschreibung wiederverwendet (`planTagInput`), derselbe Name steht bei den Vorschlägen vorn. Eine `aria-live`-Zeile sagt, was geschah; die Tasten nennt ein verborgener Hinweis per `aria-describedby`. Die Regeln des Feldes teilen sich `TagPicker` und Stichwort-Editor in `domain/list-input.ts`.
  - **Seitenpanel:** 480 px, fester Kopf (Kontext, Aktionen, „Vollansicht“, ×) und fester Fuß, Slide-in nur beim ersten Öffnen. Ab 64rem eingebettet wie in Jira: volle rechte Spalte neben der ganzen Ansicht (Kennzahlen, Filter, Abschnittsleiste, Tabelle), von der Kopfzeile (ab 64rem `sticky`, Höhe in `--app-header-height`) bis zum unteren Rand; die Ansicht staucht sich. Zwischen 36 und 64rem Overlay von rechts mit `--color-blanket`, Ansicht und Kopfzeile `inert`, Klick aufs Blanket schließt wie ×; unter 36rem volle Breite. Tabellen scrollen nie seitlich (kein `min-width`); Spalten weichen in fester Reihenfolge (Aufgaben: Erstellt, Tags, Projekt, Fällig; Eingang: Eingangsdatum, Quelle, Art, Quelldatum; Projekte: archiviert, neu, gesamt, aktiv; Wiederholungen: Projekt, Offenes Ticket, Nächstes Ticket, Rhythmus), Häkchen bzw. Auswahl, Titel und Aktionen bleiben. Alle vier Tabellen rechnen das seit SP-2 bzw. SP-5 mit `fitColumns` ([ADR-0030](docs/adr/0030-spalten-breiten-und-kompakte-zeilen.md)) über `ColumnFit` (`components/table/column-fit.svelte.ts`): Ein `ResizeObserver` misst den Rahmen, `table-layout: fixed` mit `<colgroup>`, ausgeblendete Spalten werden nicht gerendert, jede Zelle trägt `data-col`, „Weitere Spalten im Panel“ steht nur bei Spalten, die wegen Platz fehlen; Container-Queries gibt es nicht mehr (`table-columns.test.ts`). Ein Griff am rechten Rand jedes Spaltenkopfs mit änderbarer Breite (`ResizableHeader`, nur Zeiger, `aria-hidden`) ändert die Breite per Ziehen (Esc bricht ab, Doppelklick passt an; seit Nachtrag 3 auch am Titel bzw. Name: schmaler gibt den Rest gleichmäßig den anderen Spalten, breiter lässt sie bis zum Minimum schrumpfen, im engen Rahmen gibt der Titel zuerst nach, Doppelklick gibt ihm wieder den Rest; `resizeColumn`, `flexibleBounds`), gespeichert pro Gerät in `localStorage` `byl-columns-tickets|inbox|projects|recurrences` (`ColumnPrefsRegistry` im `(app)`-Layout, `storage`-Abgleich anderer Tabs); das Menü „Spalten“ steht in jeder Abschnittsleiste (Projekte nur in der Liste, Wiederholungen nur mit Regeln). Titel in „Eingang“ und „Wiederholungen“ haben ebenfalls höchstens 2 Zeilen. × und Esc führen zur Liste, außer ein Feld ist im Bearbeitungsmodus. Baustein `overlay/Drawer.svelte`, Anordnung neben der Liste `ViewWithPanel.svelte`; kein `.side-panel` mehr. Fehlt beim Schließen eines Modals der Auslöser, geht der Fokus auf die Überschrift der Ansicht (`data-view-heading` der `SectionBar`).
  - **Vollansicht:** XL-Modal mit Adresse `/tickets/<id>/voll`, zweispaltig (links Titel, Beschreibung, Kommentare und Verlauf; rechts 340 px mit Karten). Seit BI-1 ([ADR-0036](docs/adr/0036-sammelbearbeitung-inline-und-oeffnungsmodus.md) §1) **ersetzt** sie das Panel: Auf `/voll` ist das Panel nicht gemountet, die Liste steht in voller Breite dahinter, Panel und Vollansicht erscheinen nie zugleich (auch nicht über Zurück/Vor). ×, Esc und Schleier führen zur Liste ohne Panel mit Fokus auf die Zeile; unter 64rem zurück ins Panel mit Fokus auf „Vollansicht öffnen“. Im Kopf steht vor dem × „Im Seitenpanel öffnen“ (Gegenstück zu „Vollansicht“, `.button-icon`-Link mit gespiegeltem Symbol). **Öffnungsmodus:** Beide Knöpfe merken die Wahl pro Gerät (`localStorage` `byl-ticket-open`, nur `full`, „Seitenpanel“ entfernt den Schlüssel; `TicketOpenModeStore` im `(app)`-Layout, Regeln in `domain/open-mode.ts`, Links über `ticketLinks()`), nicht mit Strg/Umschalt und nicht unter 64rem. Alle Ticket-Links der App (Zeilen, Pfad, Unteraufgaben, Eingang, Wiederholungen, Ergebnisse) öffnen im gemerkten Modus, unter 64rem immer das Panel; in der Vollansicht bleiben Pfad und Unteraufgaben Links auf Vollansichten. Der Wechsel zwischen Panel und Vollansicht desselben Tickets behält Entwürfe (sie liegen in den Stores) und fragt nicht. `tickets/[id]/+layout.svelte` lädt das Ticket für Panel und Vollansicht und hält die Verwerfen-Frage (samt `discarding`); solange die Vollansicht offen ist, fragt sie inline oben im Inhalt (`TicketLeaveQuestion`, `SectionMessage` warning, Fokus auf „Weiter bearbeiten“, Esc verbraucht; angemeldet über `TicketRoute.askInline`), weil kein Dialog aus einem Dialog aufgeht, und „Löschen …“ fragt dort ebenfalls inline; Panel und Vollansicht setzen dieselben Teile zusammen (`TicketFields`, `TicketDescription`, `TicketMeta`, `TicketDelete`). Hat das Ticket Quellen, nennt die Löschabfrage deren Zahl und fragt per Radio „Quellen zurück in den Eingang“ (vorausgewählt) oder „Quellen verwerfen“ (Snippet `options` des `ConfirmDialog`, seit HK-6).
  - **Flags:** unten links, neuestes oben, höchstens drei; Erfolg und Info 8 s mit Pause bei Hover, Fokus, verborgenem Tab und offenem Modal, Fehler bleiben. Höchstens eine Aktion (etwa „Rückgängig“). Der Fokus springt nie. Feld-, Formular- und Ladefehler bleiben inline. Store `stores/flags.svelte.ts` per Kontext im `(app)`-Layout; Stores bekommen ihn als `FlagSink` (ohne ihn `SILENT_FLAGS`), Ansichten ohne eigenen Store als Prop.
  - **Erneut geöffnet und zweiter Tab ([ADR-0035](docs/adr/0035-start-einstieg-und-offene-tabs.md) §5 und §6, seit SF-3):** Das `(app)`-Layout abonniert `byl/attention` (`data/attention.ts`, ohne Optionen) und gibt die Nachricht an den `AttentionStore` (`stores/attention.svelte.ts`): erst das Ack, dann das Info-Flag „Du hast becauseyoulovejira erneut geöffnet.“ (ein Flag, auch bei mehreren Nachrichten) und das Titel-Blinken (`TitleBlinker` in `lib/title-blink.ts`: nur verborgen, jede Sekunde „● Hier ist becauseyoulovejira“, höchstens 30 s, beim Sichtbarwerden und bei `pagehide` zurück). `stop` gibt ohne Ack das neutrale Flag „becauseyoulovejira wurde beendet.“ (seit BS-3 ohne „(stop.bat)“, weil auch ein Neustart es auslöst), das bis zum Neuverbinden bleibt. Das Wurzel-Layout hält den `BroadcastChannel` `byl-tabs` (`lib/tab-presence.ts`, Kontext für das `(app)`-Layout, auf `/login` blinkt nur der Titel): Ein Tab von außerhalb der App (`shouldCheckForDuplicate`: Referrer leer oder fremd, Navigation `navigate`, keine Marke `byl-tab-keep` in `sessionStorage`, nicht `display-mode: standalone`) fragt 300 ms nach `here`; antwortet ein Tab, bekommt der `attention` und der neue zeigt `DuplicateTabNotice` (Modal S „Die App ist schon offen“, schließt sich nach 5 s, erster Fokus und Esc: „Hier weiterarbeiten“, dazu „Tab schließen“; scheitert `window.close()`: „Du kannst diesen Tab jetzt schließen.“). Texte in `lib/guidance/texts.ts`.
  - **„Rückgängig“ (seit UI-5):** Erledigen per Häkchen und Verwerfen im Eingang nehmen die Zeile sofort heraus; das Flag bietet „Rückgängig“ 8 s lang (Undo-Fenster = Laufzeit des Flags, pausiert wie oben). Danach geht es nur noch über den normalen Weg (Status ändern, „Wiederherstellen“). Fehler von Zeilenaktionen erscheinen als Fehler-Flag.
  - **Auswahl und Sammelaktionen (seit BI-2, [ADR-0036](docs/adr/0036-sammelbearbeitung-inline-und-oeffnungsmodus.md) §2 bis §5):** Die Tabelle „Aufgaben“ hat vorn die feste Spalte „Auswahl“ (2,5rem, Pflicht, nicht im Menü „Spalten“; Checkbox „HAUS-12 auswählen“, getrennt vom Häkchen „HAUS-12 erledigt“; die ganze Zelle ist das `label` und öffnet nie das Ticket). Umschalt+Klick wählt einen Bereich in der Bildschirm-Reihenfolge, die Kopf-Checkbox „Alle angezeigten Tickets auswählen“ alle gefilterten Tickets (auch in zugeklappten Gruppen, `indeterminate` bei einem Teil), Esc in Tabelle oder Leiste hebt die Auswahl auf, nach einem Filterwechsel bleiben nur angezeigte Tickets gewählt (reine Regeln in `domain/selection.ts`). Ab einer Auswahl steht über der Tabelle die Leiste `BulkActionBar` (Glas thick, `sticky`; seit PB-2 liegt das Glas im gemeinsamen Baustein `SelectionBar`, den auch der Papierkorb nutzt): „N Tickets ausgewählt“, „Fälligkeit …“ (Modal S: setzen, verschieben um Tage/Wochen, leeren, „Datum der Quelle übernehmen“), „Priorität“ und „Status“ (Menüs), „Projekt …“ (Modal S, neuer Key je Ticket), „Tags …“ (Modal M, hinzufügen mit `TagPicker` oder entfernen per Checkbox), „Erledigen“ (Frage mit „Unteraufgaben mit erledigen“ nur bei offenen blockierenden Unteraufgaben), „Löschen …“ (`ConfirmDialog` „N Tickets in den Papierkorb verschieben?“, Quellen-Wahl wie einzeln; seit PB-2 mit „Rückgängig“ = Wiederherstellen mit `expected_updated`, übergeordnete Tickets zuerst), „Auswahl aufheben“. Der `BulkEditStore` (`stores/bulk-edit.svelte.ts`, im `(app)`-Layout; Regeln in `domain/bulk.ts`) schickt je Ticket eine Anfrage über die Record-API bzw. die Löschroute, höchstens 4 zugleich, zeigt einen Fortschrittsbalken, nennt Probleme je Ticket unter der Leiste (Fehler als `.alert-error`, Übersprungenes neutral) und bietet nach Feldänderungen, „Erledigen“ und „Löschen“ im Flag 8 s „Rückgängig“ (mit `expected_updated`, zwischenzeitlich Geändertes wird nicht überschrieben; Konflikte einer Serie nach `reopenConflicts` stehen im Ergebnis). „Datum der Quelle“ gilt nur für Tickets, deren Hauptquelle ein Termin (`kind = event`) mit Datum ist (`listSourceEventDates`); „Gesammelt umwandeln“ hat dafür bei Terminen die Checkbox „Datum des Termins als Fälligkeit“ (aus).
  - **Bearbeiten in Zellen (seit BI-3, [ADR-0036](docs/adr/0036-sammelbearbeitung-inline-und-oeffnungsmodus.md) §6):** Priorität, Status, Projekt, Tags und Fälligkeit der Tabelle „Aufgaben“ sind Knöpfe, die die Zelle füllen (`components/table/EditableCell.svelte`, Name „Priorität von HAUS-12: Hoch, ändern“, beim Zeigen und Fokus eine dezente Füllung und ein Stift), und öffnen ein kleines Popover: Menüs (`menuitemradio`) für Priorität, Status und Projekt („Kein Projekt“ und die aktiven Projekte in Baum-Reihenfolge), ein Formular für die Fälligkeit (`DueEditor`: Datum, „Übernehmen“, „Leeren“) und die Tag-Eingabe (`TagPicker`, jede Änderung speichert sofort). Ein Klick in diese Zellen oder ins Popover öffnet nie das Ticket, außerhalb davon öffnet der Zeilenklick es im gemerkten Modus. Tab erreicht die Zellen, Enter öffnet, Esc schließt ohne zu speichern, der Fokus kehrt zur Zelle zurück. Gespeichert wird über `TicketListStore.changeField` mit der Record-API wie im Panel (neuer Key beim Projektwechsel, Verlauf, Serie); „Erledigt“ läuft über `setDone` mit der Frage zu Unteraufgaben und „Rückgängig“ im Flag. Seit EH-13 gibt es die geführte Tour (`lib/tour/tour.ts`, Schritte in `lib/tour/steps.ts` auf `data-tour`-Attributen: Schnellerfassung, Eingang, Filterleiste, Projekte Liste/Kacheln, Kanal-Katalog; die Tour wechselt dafür die Seite und überspringt fehlende Ziele), gestartet nur über „Kurze Einführung“ im „?“-Menü und „Erste Schritte“; Esc beendet sie, der Fokus kehrt zum Auslöser zurück, bei `prefers-reduced-motion` ohne Animation, Schleier `--color-blanket` über `overlayColor`. Eine optionale Tour mit driver.js (lokal gebündelt, nur manuell startbar, höchstens etwa 5 Schritte) ist die einzige Ausnahme von „keine UI-Bibliothek“.
  - Bis ein Paket gemergt ist, gilt für seinen Bereich die Beschreibung oben.
- Inhalte aus Kanälen sind nicht vertrauenswürdig: Anzeige nur über `Markdown.svelte`, Links nur `http:`/`https:`/`mailto:`, Bilder aus Mails werden nie geladen.
- Realtime: Subscriptions aktualisieren gezielt einzelne Datensätze; kein Polling, kein komplettes Neuladen. Jedes Abo läuft über `hold` (`stores/realtime.ts`, [ADR-0007](docs/adr/0007-realtime-und-sitzungspflege.md) Nachtrag): Ein gescheitertes Abo wird nach 1, 2, 5, 10 und dann alle 30 s erneut versucht, der Besitzer gleicht danach ab (`recovered`), und nur die Rückrufe des aktuellen Versuchs wirken (`guard`, das SDK behält Listener gescheiterter Versuche). Solange eines fehlt, zeigt das `(app)`-Layout `LiveUpdateNotice` (Warnung ohne Rot, „Neu laden“, `LiveHealth`).
- **Neue Version im offenen Tab ([ADR-0040](docs/adr/0040-veroeffentlichen-ohne-unterbrechung.md)):** Meldet SvelteKit über `updated` eine neue Version, zeigt das `(app)`-Layout `AppUpdateNotice` (`SectionMessage` info, „Eine neue Version von becauseyoulovejira ist da.“, „Neu laden“, bei ungespeicherten Eingaben der Satz `APP_UPDATED.unsaved`). Der nächste Klick auf einen Link lädt sein Ziel als neues Dokument (`onNavigate`, also erst nach der Frage „Änderungen verwerfen?“), außer Eingaben des Tickets, eine laufende Sammelaktion oder ein angebotenes „Rückgängig“ gingen verloren (`shouldReloadOnNavigate` in `lib/app-update.ts`). `hooks.client.ts` macht aus jedem Fehler eine deutsche Meldung ohne Technik und markiert Module, die nicht geladen werden konnten (`kind: 'module-load'`, auch bei Preloads, daher ohne Nebenwirkung); die Fehlerseite `+error.svelte` lädt dann die Adresse einmal neu (sessionStorage `byl-reload-attempt`, 60 s je Adresse), sonst „Neu laden“ und „Zur Übersicht“. Die Notfallseite `src/error.html` (wenn nicht einmal Wurzel-Layout oder Fehlerseite laden) ist deutsch, in Systemfarben, mit „Neu laden“ als Knopf mit `onclick`, weil SvelteKit sie ohne Skripte einsetzt.
- Bereichs-Umschalter: „Privat" aktiv, „Haushalt" ausgegraut, nicht klickbar (`aria-disabled`), darin ein dezentes Etikett „Demnächst" (`Lozenge` `muted`, per `aria-describedby`), kein dritter Eintrag.
- Markdown-Ausgabe wird sanitisiert ([ADR-0008](docs/adr/0008-markdown-rendering-und-sanitizing.md)). Seit RT-1 ([ADR-0032](docs/adr/0032-editor-tiptap-markdown.md), [Plan Editor](docs/plan/editor.md)) kennt die Anzeige zwei Erweiterungen: `++Text++` wird unterstrichen (`markdown-it-ins`, MIT, Ausgabe `<u>`), und `- [ ]`/`- [x]` in Aufzählungen wird eine Checkliste (eigenes Plugin in `lib/markdown.ts`, nicht in nummerierten Listen). Die Checkbox ist deaktiviert, trägt den Text der Aufgabe als Namen, und ihr `li` hat den Index in `data-task`. DOMPurify lässt dafür nur `u`, deaktivierte Checkboxen und Ziffern in `data-task` zu (Hook in `lib/markdown.ts`). Der Testkorpus liegt unter `web/src/lib/test/markdown-corpus/`.
  - **Abhaken in der Ansicht (seit RT-2):** `Markdown.svelte` macht die Checkboxen mit `ontoggletask` im DOM bedienbar (ein `change`-Handler am Container, kein zweites rohes HTML), in der Beschreibung und in eigenen Kommentaren; fremde Kommentare, Vorschau und Eingang bleiben gesperrt. `toggleTask` in `lib/markdown.ts` ändert genau das Zeichen zwischen den Klammern der Aufgabe (derselbe Parser wie die Anzeige). Während des Speicherns sind alle Kästchen `aria-disabled`, das gedrückte `aria-busy`; ein Fehler setzt es zurück.
  - **Editor (seit RT-3, [ADR-0032](docs/adr/0032-editor-tiptap-markdown.md), [Plan Editor](docs/plan/editor.md) §4):** `RichTextEditor` in Beschreibung, Kommentaren (kompakt ohne Textstil; der neue Kommentar öffnet erst über „Kommentar hinzufügen …“, damit das Öffnen eines Tickets nichts lädt), „Neues Ticket“ und Regel-Vorlage lädt Tiptap beim ersten „Bearbeiten“ per `import()` (`lib/editor/**` nur so, `editor-lazy.test.ts`) und liest und schreibt Markdown über die Brücke `lib/editor/markdown-bridge.ts` (`prosemirror-markdown` auf der markdown-it-Instanz der Anzeige). Der Entwurf ändert sich nur bei einer echten Änderung; unverändert gespeichert wird nichts. `richEditable` öffnet Tabellen, Listen aus Aufgaben und normalen Punkten, Unbekanntes und alles, dessen Anzeige sich nach einer Rundreise ändern würde, im Quelltextmodus mit Hinweis; scheitert das Laden, übernimmt die `textarea`. Formatierungsleiste nach WAI-ARIA (`role="toolbar"`, Roving-Tabindex, Pfeiltasten, Alt+F10 hinein, Esc zurück; Textstil und „Weitere Formatierungen“ als Popover-Menüs, unter 560 px Listen und Blöcke im Menü „Listen und Blöcke“), rechts „Markdown“ (`aria-pressed`) als Quelltextmodus. Kürzel wie Jira aus `domain/shortcuts.ts` (Abschnitt „Editor“), Eingaberegeln für Markdown samt `++x++`. Seit RT-4 öffnet „/“ am Zeilenanfang oder nach einem Leerzeichen das Menü „Blöcke“ (`lib/editor/slash.ts`, eigenes ProseMirror-Plugin, Liste `SuggestionList` am Cursor; Textfeld mit `aria-autocomplete`, `aria-controls`, `aria-activedescendant`; Enter oder Tab fügt ein, Esc schließt), und „Link“ (Knopf der Leiste, Strg+K, „/link“) öffnet ein Popover `panel` mit „Adresse“ und „Text“ (nur http, https, mailto über `domain/link.ts`, Fehler am Feld, „Link entfernen“ bei einem Link). Seit RT-5 bereinigt `lib/editor/paste.ts` eingefügtes HTML (Word, Google Docs, LibreOffice: Kommentare, Stile, Office-Tags, Bilder, Formulare und Skripte weg, Word-Listen zu `ul`/`ol`, Stil-Formatierung zu `strong`/`em`/`u`/`s`, nur `href` mit http, https, mailto und `start` bleiben); Text mit Markdown wird als Markdown gelesen, Strg+Umschalt+V fügt immer reinen Text ein (Tiptaps Einfüge-Regeln sind aus). Esc wird im Editor verbraucht. Anzeige und Editor teilen `lib/styles/prose.css`; die Fläche ist undurchsichtig, ohne Glas.
  - **Kein stilles Überschreiben der Beschreibung:** Abhaken und Speichern senden das Body-Feld `expected_updated` (nicht gespeichert). Der Ticket-Hook liest das Ticket in seiner Transaktion neu und lehnt bei anderem `updated` mit `validation_description_stale` ab. Hat sich nur ein anderes Feld geändert, sendet der `TicketDetailStore` einmal erneut auf dem neuen Stand. Sonst meldet das Abhaken „Die Beschreibung wurde inzwischen geändert. Bitte erneut abhaken.“, und das Speichern fragt **inline** im Abschnitt „Beschreibung“ „Überschreiben“ oder „Verwerfen und neu laden“ (keine Bestätigung, weil aus der Vollansicht kein Dialog aufgeht). Kommentare haben keine solche Prüfung, nur ihr Autor darf sie ändern. Der Verlauf nennt ein reines Abhaken „Aufgabe abgehakt: …“ bzw. „Aufgabe wieder offen: …“ (`history-format.ts`).

## 8. Design-System

Alle Farben als CSS-Custom-Properties zentral in `web/src/lib/styles/tokens.css`. Minimalistisch, feine Linien, wenig Farbe; **genau eine Akzentfarbe je Theme** (Standard Petrol, [ADR-0027](docs/adr/0027-akzent-themes.md)). Keine Farbwerte außerhalb von `tokens.css`.

- **Akzent-Themes ([ADR-0027](docs/adr/0027-akzent-themes.md) mit Nachtrag 2026-09-27):** Petrol (Standard), Rubin, Smaragd, Kupfer, jedes hell und dunkel, unabhängig vom Modus. Purpur ist entfallen, Honig heißt jetzt Kupfer.
  - Die vier Modus-Blöcke tragen alle Tokens mit Petrol.
  - Jedes weitere Theme hat vier Blöcke mit `data-accent` am Wurzelelement. Dort stehen genau die Akzent-Tokens: `--color-brand`, `--color-brand-text`, `--color-brand-soft-bg`, `--color-brand-soft-text`, `--color-on-brand`, `--status-open-text|border`, `--status-in-progress-bg|text`, `--color-danger`, `--color-danger-soft-bg` und `--status-waiting-bg|text|border`.
  - Neutrale Flächen, Linien, Text und der Schleier sind in allen Themes gleich, ebenso Materialien, Füllungen und Schatten ([ADR-0029](docs/adr/0029-glas-materialien.md)).
  - Eine neue akzentabhängige Farbe braucht ein Token in allen Themes.
  - `tokens.test.ts` prüft für 4 Themes × 4 Varianten:
    - Vollständigkeit der Tokens
    - WCAG AA: Text 4,5 : 1, Fokusring und UI-Elemente 3 : 1
    - Abstände (ΔE2000): Akzent zu Fehler ≥ 20, Smaragd zu Petrol ≥ 20, Themes untereinander ≥ 20, Fehler zu „Wartet“ ≥ 15

- **Hell/Dunkel ([ADR-0025](docs/adr/0025-ui-konsistenz-overlay-system.md) §10):** Standard ist die Systemeinstellung. Der Umschalter in der Kopfzeile (Menü „Hell“, „Dunkel“, „Wie System“) und seit EH-8 die Seite „Einstellungen → Darstellung“ (dieselbe Wahl als Radiogruppe, derselbe `ThemeStore`) speichern die Wahl in `localStorage` unter `byl-theme` (`light` oder `dark`; „Wie System“ entfernt den Schlüssel), nur lokal, nicht pro Nutzer bis E7. Das Inline-Skript in `app.html` setzt `data-theme` vor dem ersten Rendern (FOUC-Schutz), prüft den Wert, fängt Fehler des Speichers ab und übernimmt einmalig den alten Schlüssel `td-theme`. Jeder der vier Modus-Blöcke von `tokens.css` setzt `color-scheme`, damit native Controls dem Modus folgen.
- **Farbwahl ([ADR-0027](docs/adr/0027-akzent-themes.md) §6):**
  - Das Menü „Darstellung“ hat nach einem Trenner die Gruppe „Farbe“ (`menuitemradio` mit Farbfeld). Die Seite „Einstellungen → Darstellung“ hat die Radiogruppe „Farbe“.
  - Beide nutzen `ACCENT_THEMES`, `ACCENT_LABELS` und den `AccentStore` aus `lib/accent.svelte.ts`.
  - Gespeichert wird in `localStorage` unter `byl-accent`, nur `rubin`, `smaragd` oder `kupfer`. „Petrol“ entfernt den Schlüssel und `data-accent`. Ein `storage`-Listener gleicht andere Tabs ab.
  - Das Inline-Skript in `app.html` setzt `data-accent` vor dem ersten Rendern, in einem eigenen `try` mit derselben Allowlist (`theme-boot.test.ts` gleicht Schlüssel und Liste ab). Alte Werte (`LEGACY_ACCENTS`) schreibt es einmal um: `honig` → `kupfer`, `purpur` → Petrol (Schlüssel entfernt); `parseAccent` liest sie genauso.
  - Die Farbfelder kommen aus `--swatch-<theme>` in den Modus-Blöcken. Der Test prüft, dass jedes Feld dem Akzent seines Themes gleicht.
- **Overlay-Tokens (ADR-0025 §2):** `--color-blanket` (einzige neue Farbe, dunkler Schleier hinter Modals, in allen vier Blöcken). Nicht farbig und nur in `:root`: `--overlay-width-s|m|l|xl` (25/37.5/50/62.5rem), `--overlay-max-height` und `--overlay-max-height-xl`, `--drawer-width` (30rem), `--full-view-sidebar` (21.25rem), `--radius-control` (0.375rem), `--radius-surface` (seit G-4 0.625rem, Tabellenrahmen, Kacheln, Karten), `--motion-fast` (120ms), `--motion-medium` (200ms), `--motion-ease`; seit ADR-0029 dazu `--radius-overlay` (0.75rem, Overlays auf Glas), `--radius-item` (0.25rem, Menüzeile, Segment, kleine Kennzeichen), `--radius-pill` (999px, Switch, Chips, Zähler, Pillen), `--control-height-s|m|l` (1.5/1.75/2.25rem) und `--glass-filter-regular|thick`. Neue Radien und Maße nur über diese Tokens: `border-radius` nur als `var(--radius-*)`, `0`, `50%` oder `inherit` (`no-own-radii.test.ts`; Ausnahmeliste für drei Dateien der Mail-Arbeit, die nur schrumpfen darf). Tests der Overlays nutzen die gemeinsamen Stubs aus `web/src/lib/test/overlay-stubs.ts` statt eigener `showModal`-Attrappen.
- **Materialien und Tiefe ([ADR-0029](docs/adr/0029-glas-materialien.md), Pakete G-1 bis G-6 nach [docs/plan/e6-glas.md](docs/plan/e6-glas.md)):**
  - Glas nur in der Bedienebene (Kopfzeile, Seitenpanel, Einstellungsnavigation, Popover und Menüs, Modals S bis L, Flags, Anmeldung, Tour) über `--material-regular|thick` und `--glass-filter-regular|thick`; `backdrop-filter` nur in den Dateien der Allowlist von `glass-allowlist.test.ts` und nur mit diesen Tokens. `--material-regular` nur dort, wo darunter der Verlauf oder Tabellen scrollen.
  - Tabellen, Kacheln, Karten, Texte, Formulare, Vollansicht und Blanket bleiben undurchsichtig. Kein Glas im Glas; Kopfzeile und Seitenpanel haben keine Nachfahren mit `position: fixed`.
  - Mindest-Deckkraft 0,82, geprüft in `glass-contrast.test.ts` für alle Themes × vier Modus-Blöcke × Materialien gegen jede Farbe der Palette.
  - Schatten nur über `--shadow-*` (neutral, nur in den Modus-Blöcken) und immer mit Linie (`--color-separator` auf Glas); dazu nur die Lichtkante `inset 0 1px 0 var(--glass-edge)` und die Zeilenmarkierung `inset 3px 0 0 var(--color-brand)`.
  - Der Hintergrund ist ein Verlauf aus `--color-brand-soft-bg` auf `body::before` (nur dort, `body` selbst malt keinen Hintergrund).
  - Ein Umschaltpunkt in `tokens.css` macht alles undurchsichtig (`!important`, weil die Modus-Blöcke spezifischer sind): `prefers-reduced-transparency: reduce`, `prefers-contrast: more` (dazu Trennlinien in `--color-text-muted`, keine Schatten), `forced-colors: active` und fehlendes `backdrop-filter`; dazu der Schalter „Transparenz“ (`:root[data-transparency='off']`). Die Systemeinstellung gewinnt immer.
  - **Schalter „Transparenz“ (seit G-3):** Switch „Glas-Effekt“ in der Gruppe „Transparenz“ unter „Einstellungen → Darstellung“, standardmäßig an. `TransparencyStore` in `lib/transparency.svelte.ts` speichert in `localStorage` unter `byl-transparency` nur `off` („an“ entfernt den Schlüssel) und setzt `data-transparency="off"`. Das Inline-Skript in `app.html` setzt das Attribut vor dem ersten Rendern in einem eigenen `try` (`theme-boot.test.ts`). Ein `storage`-Listener gleicht andere Tabs ab (verbunden in `ThemeMenu`, das auf jeder Seite steht). Meldet `matchMedia('(prefers-reduced-transparency: reduce)')` die Systemeinstellung, zeigt die Seite einen Hinweis (`SectionMessage` info); der Schalter bleibt bedienbar.
  - **Switch:** `input[type='checkbox'][role='switch']`, gestaltet allein in `base.css` über die Rolle, nicht über eine Klasse (lokale `.switch`-Klassen sitzen auf Labels); Knopf links in `--color-text-muted`, an rechts in `--color-on-brand` auf `--color-brand`, `--radius-pill`, gleitet mit `--motion-fast`, in `forced-colors` die native Checkbox. `role="switch"` nur auf Checkboxen (`no-own-controls.test.ts`). Einsatz nach Apple HIG (seit G-5): Switch für eine betonte Einzeleinstellung („Glas-Effekt“, „Erledigte anzeigen“, „Archivierte anzeigen“ und seit dem Plan [Spalten](docs/plan/e6-spalten.md) die zwei Schalter im Kanal-Dialog `ChannelEditModal`: Telegram „Auf Nachrichten ohne Stichwort antworten“, Postfach „Betreff, Absender, Kopfzeilen und Text durchsuchen“, je als Zeile mit dem Namen links und dem Switch rechts), Checkboxen für Listen und Auswahl (Eingang, Postfach-Auswahl, Wochentage, Erledigt-Häkchen der Zeile, Menü „Spalten“).

- **Steuerskript ([ADR-0039](docs/adr/0039-betriebsskripte.md), [Plan Betriebsskripte](docs/plan/betriebsskripte.md), seit BS-1):** `app/byl-control.ps1 <Befehl>` mit `start`, `stop`, `restart`, `reload`, `status`, `open`, `logs`, `doctor`, `port`, `autostart-on`, `autostart-off`, `reset-admin`, `help`; Exit-Codes 0 erledigt (bei `status`: läuft und aktuell), 1 Fehler, 2 Einrichtung offen, 3 läuft nicht, 4 Port belegt, 5 antwortet nicht, 6 Neustart nötig; `-Json` für `status` und `doctor`. Reine Logik in `byl-functions.ps1` (ASCII): `Set-BylAddress` stellt alle Adressen auf den Port (`byl-config.json`, Standard 8090, 1024–65535, ungültig: Abbruch); eigene Instanz nur über Programmpfad in diesem Ordner plus `serve`, `--http=127.0.0.1:<Port>` und `--dir` auf `pb_data` (`Select-AppProcess`), Mail-Hilfsprozess ebenso (`Select-MailHelperProcess` mit den Adressen der eigenen Instanz; ein von `build-mail-helper.ps1` umbenannter läuft für Windows weiter als `byl-mail.exe`); Zustandsdatei `run/byl.state.json` (PID, Port, Startzeiten; gilt nur bei gleicher PID und Startzeit, sonst gelöscht); `Resolve-StartAction` (läuft: nur Browser; antwortet nicht: Exit 5, Neustart nur mit `-Force`; Port fremd: Exit 4 mit Programmpfad, nächstem freien Port und Befehl, nie ausweichen). `stop` beendet geordnet (`Stop-Gracefully`: `CTRL_BREAK_EVENT` über einen PowerShell-Kindprozess mit `AttachConsole`, nur an eine Konsole, die dem Ziel allein gehört; PocketBase schließt die Datenbank, die WAL wird übertragen), erst nach 15 s hart mit Warnung, erst Mail-Hilfsprozess, dann PocketBase, dann warten auf den freien Port. ## 11. Regeln für Agenten und Automatisierung auf dem Entwicklungsrechner

1. **Python-Verbot:** `python`, `python3` oder `py` aufrufen ist untersagt (öffnet auf Windows den Microsoft Store). JSON wird stattdessen mit `node -e` oder PowerShell `ConvertFrom-Json` geparst. Andere Skriptaufgaben nutzen node.js oder PowerShell.

2. **PocketBase-Sicherheit:** PocketBase darf nicht mit `serve` in einem Datenordner ohne Superuser gestartet werden (sonst öffnet sich der Browser mit dem Installer). Tests und Spikes, die einen laufenden Server brauchen, erstellen vorab einen Wegwerf-Superuser in einem Wegwerf-Datenordner:
   ```powershell
   $tempDir = Join-Path $env:TEMP ("td-spike-" + [guid]::NewGuid().ToString('N'))
   $email   = "spike-$([guid]::NewGuid().ToString('N'))@example.com"
   $bytes   = New-Object byte[] 24
   $rng     = [System.Security.Cryptography.RandomNumberGenerator]::Create()
   $rng.GetBytes($bytes); $rng.Dispose()
   $pass    = [Convert]::ToBase64String($bytes)
   $server  = $null
   try {
       New-Item -ItemType Directory -Path $tempDir | Out-Null
       & ./app/pocketbase.exe superuser upsert --dir="$tempDir" $email $pass
       if ($LASTEXITCODE -ne 0) { throw "superuser upsert failed ($LASTEXITCODE)" }
       $server = Start-Process -FilePath ./app/pocketbase.exe -PassThru -NoNewWindow `
           -ArgumentList 'serve', "--dir=$tempDir", '--http=127.0.0.1:8099'
       # Tests gegen http://127.0.0.1:8099 ausführen (Login mit $email / $pass)
   }
   finally {
       if ($server -and -not $server.HasExited) { Stop-Process -Id $server.Id -Force }
       if ($server) { $server.WaitForExit() }
       Remove-Item -Recurse -Force -ErrorAction SilentlyContinue $tempDir
   }
   ```
   Zugangsdaten werden zur Laufzeit erzeugt und niemals ins Repo geschrieben.

3. **Keine Autostart-Skripte und Hintergrundprozesse:** Nie `start.bat`, `stop.bat`, `start-hidden.vbs`, Autostart-Skripte oder `byl-control.ps1` für die Instanz des Nutzers ausführen (`app\` eines Klons, Port 8090); keinen Dev-Server oder Browser-Fenster öffnen. Erlaubt ist `byl-control.ps1` nur im Worktree gegen eine Wegwerf-Kopie der Laufzeitteile außerhalb von `app\` (wie `tests/integration/control-script.test.mjs`: eigener Datenordner mit Wegwerf-Superuser, Zufallsport, immer `-NoBrowser`, bereinigte Umgebung mit `BYL_TEST_ISOLATED=1`, damit die Kopie keine `BYL_*`-Variablen des Kontos liest); vor jedem Lauf prüfen, dass alle Pfade dorthin zeigen. Kindprozesse startet ein Test nur über `tests/support/clean-env.mjs` (`spawnClean`, `spawnSyncClean`; [Plan Test-Härtung](docs/plan/test-haertung.md)). Die kopierte `pocketbase.exe` nicht unter `%TEMP%` ablegen (PocketBase schaltet dort in den Dev-Modus). Jeder gestartete PocketBase-Server oder andere Hintergrundprozess wird vor Ende der Aufgabe beendet (try/finally oder afterAll); der Temp-Datenordner wird gelöscht.

4. **Nur eine Claude-Session pro Repo:** Nicht mehrere schreibende Agenten in `main` parallel ausführen. Konflikte abfangen und eskalieren.

5. **Texte nie über die Shell schreiben:** Eine Shell führt Befehle in Backticks bzw. `$(…)` innerhalb von Heredocs und doppelt gequoteten Zeichenketten aus. So hat ein Agent beim Schreiben einer Markdown-Datei versehentlich Beispielbefehle gestartet.
   - Markdown- und Textdateien (Doku, Pläne, ADRs, PR-Texte, Commit-Nachrichten) werden ausschließlich mit den Datei-Werkzeugen (Write/Edit) geschrieben, nie per Shell-Heredoc, `echo`, `printf` oder Umleitung. PR-Texte und Commit-Nachrichten entstehen als Datei im Scratchpad und gehen per `gh pr create --body-file` bzw. `git commit -F` an Git.
   - Beispielbefehle mit `setx`, `stop.bat`, `start.bat` oder anderen Start- und Stopp-Skripten stehen nie in einer Shell-Befehlszeile, auch nicht als Text in Anführungszeichen. Sie gehören nur in Dateien, die mit Write/Edit entstehen.

6. **Bauen, während die App des Nutzers läuft ([ADR-0040](docs/adr/0040-veroeffentlichen-ohne-unterbrechung.md)):** Im Live-Ordner wird die Oberfläche nur über `scripts\build.ps1` bzw. das Root-`npm run build` gebaut; beide veröffentlichen ohne Lücke, und offene Tabs arbeiten weiter. Nie `vite build` mit Ausgabe nach `app/pb_public`, nie `app/pb_public` leeren oder löschen, nie Dateien unter `_app/immutable` von Hand entfernen (offene Tabs laden sie noch). Ändert ein Merge `pb_hooks` oder `pb_migrations`, braucht die Instanz einen Neustart; den führt der Nutzer aus (Regel 3), der Agent nennt ihn im Bericht.
