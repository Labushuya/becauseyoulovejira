## 1. Ziel und Abgrenzung

**In E1:**

- Alle elf Collections aus CLAUDE.md §5 per handgeschriebener Migration, inklusive Indizes und API-Regeln.
- Hooks: Scope, atomare Key-Vergabe über `ticket_counters`, `completed_at`, Ticket-Historie (Anlage und Änderungen), Integritäts-Guards (Projekt-Code, Relationen im selben Scope, Parent maximal eine Ebene).
- Settings per Migration: automatische Backups ([ADR-0003](../adr/0003-pb-data-und-backups.md)), gesperrte Selbstregistrierung ([ADR-0002](../adr/0002-erststart-und-superuser.md)).
- Test-Harness mit Wegwerf-Instanz ([ADR-0004](../adr/0004-teststrategie-hooks-migrationen.md)), Unit-, Migrations-, Regel- und Hook-Tests.
- Frontend: Login, Logout, Session-Wiederherstellung, Route-Guard über das PocketBase JS SDK. Nach dem Login zeigt die App nur eine leere Startseite.
- Erststart-Hinweis in `start.bat` und auf der Login-Seite, README-Abschnitte „Erster Start“ sowie „Backup und Wiederherstellung“.

**Nicht in E1:** Ticket-Liste und -Detail, CRUD-UI, Kommentare-UI und Realtime-UI (E2); Projekte-, Tags- und Filter-UI (E3); Regelparameter von `recurrence_rules`, `recurrence.js`, `berlin-time.js` und Cron (E4); Schnellerfassung und Theme (E5); Logik von Stufe 2 (Abhängigkeits-Automation, Zyklenprüfung, Fortschritt); Haushalts-UI.

## 2. Querschnittsregeln für alle Pakete

- **API-Disziplin (CLAUDE.md §3):** Vor jedem Hook- und Migrationscode die Doku der gepinnten Version 0.40.4 prüfen (pocketbase.io/docs, pocketbase.io/jsvm). Jeder Handler ruft `e.next()` auf. `require(\`${__hooks}/lib/<name>.js\`)` steht **im** Handler. Filter mit Eingaben laufen immer parametrisiert.
- **Transaktionen (Befund, siehe OF-1):** In 0.40.4 laufen Create und Update über die Record-API **nicht** automatisch in einer Transaktion (`apis/record_crud.go` → `form.Submit()` → `app.SaveWithContext`; nur Delete mit Kaskaden nutzt `RunInTransaction`). Hooks, die mehrere Schreibvorgänge atomar brauchen, öffnen die Transaktion selbst (`e.app.runInTransaction((txApp) => { e.app = txApp; … e.next(); … })`) und nutzen darin nur `txApp` bzw. `e.app`.
- **Zeitzone ([ADR-0005](../adr/0005-zeitzone-europe-berlin.md)):** `new Timezone(...)` und `new DateTime(x, "Europe/Berlin")` sind verboten, weil sie ohne tzdata stillschweigend UTC liefern.
- **Logik in `lib/`:** Die `*.pb.js`-Dateien bleiben dünn. Rechen- und Entscheidungslogik gehört in reine CommonJS-Module unter `app/pb_hooks/lib/` (ES5, ohne `$app`), damit Vitest sie ohne Server testen kann.
- **Migrationen:** Dateiname `<Unix-Zeitstempel>_<beschreibung>.js`, eine fachliche Einheit pro Datei, jede Migration mit funktionierendem Rollback. Neue Collections bekommen **explizit** `autodate`-Felder `created`/`updated`, denn seit PocketBase 0.23 werden sie nicht mehr automatisch angelegt. Ausnahme: `ticket_counters`, siehe Paket 5.
- **Qualitäts-Gates vor jedem Commit mit Code:** `npm run check`, `npm run lint`, `npm test` grün. Ein Commit pro Paket (Conventional Commits; in E1 noch direkt auf `main`, seit E3 über Branch und Pull Request nach CLAUDE.md §12).
- **Agentenregeln (CLAUDE.md §11):** kein Python, kein `serve` ohne vorheriges `superuser upsert` im Wegwerf-Ordner, keine Start- oder Autostart-Skripte ausführen, alle Prozesse und Temp-Ordner aufräumen.

## 3. Datenmodell-Spezifikation (Soll für die Migrationen)

Namen, Enums, Regeln und Key-Schema stammen exakt aus CLAUDE.md §5. Feldtypen, Längen, Kaskaden und Indizes, die CLAUDE.md offenlässt, sind **Vorschläge** und mit dem Verweis auf die zugehörige offene Frage (OF-n) markiert.

Abkürzungen: `rel(X)` = Relation auf X, `req` = required, `casc` = cascadeDelete. `owner`/`household` bedeutet immer `owner rel(users) req, kein casc` und `household rel(households) optional, kein casc` (OF-6).

| Collection | Felder (Typ) | Indizes |
|---|---|---|
| `users` (Auth, existiert) | Standardfelder von PocketBase (`email`, `password`, `name`, `avatar`, `verified` …), unverändert | Standard |
| `households` | `name` text req max 100; `created`, `updated` | – |
| `household_members` | `user` rel(users) req casc; `household` rel(households) req casc; `role` select req [`owner`, `member`] (OF-7); `created`, `updated` | UNIQUE (`household`, `user`) |
| `projects` | `name` text req max 100; `code` text req, Pattern `^[A-Z]{2,6}$`; `archived` bool; `scope` text (Hook); `owner`; `household`; `created`, `updated` | UNIQUE (`scope`, `code`); (`owner`) |
| `tags` | `name` text req max 50; `owner`; `household`; `scope` text (Hook, OF-8); `created`, `updated` | UNIQUE (`owner`, `name`) laut CLAUDE.md bzw. (`scope`, `name` COLLATE NOCASE) laut OF-8 |
| `recurrence_rules` | `title` text req max 200; `description` text max 100000; `project` rel(projects) optional; `tags` rel(tags) multi; `priority` select [`low`,`medium`,`high`,`urgent`]; `mode` select req [`calendar`,`after_completion`]; `next_due` date; `last_generated_at` date; `active` bool; `owner`; `household`; `created`, `updated`. Regelparameter folgen in E4 (OF-9) | (`owner`); (`active`, `next_due`) |
| `tickets` | `number` number (ganzzahlig, min 1); `key` text; `title` text req max 200; `description` text max 100000, Markdown (OF-10); `status` select req [`backlog`,`open`,`in_progress`,`waiting`,`done`]; `priority` select req [`low`,`medium`,`high`,`urgent`]; `due` date; `project` rel(projects) optional; `tags` rel(tags) multi; `completed_at` date; `parent` rel(tickets) optional, kein casc; `blocks_parent` bool (Standard true, OF-11); `recurrence` rel(recurrence_rules) optional, kein casc; `scope` text (Hook); `owner`; `household`; `created`, `updated` | UNIQUE (`scope`, `key`); (`owner`); (`project`); (`status`); (`due`); (`parent`) |
| `comments` | `ticket` rel(tickets) req casc; `author` rel(users) req; `body` text req max 20000, Markdown; `created`, `updated` (OF-5) | (`ticket`, `created`) |
| `ticket_history` | `ticket` rel(tickets) req casc; `field` text req; `old_value` text; `new_value` text; `user` rel(users) optional (OF-4); `created` autodate | (`ticket`, `created`) |
| `dependencies` | `blocker` rel(tickets) req casc; `blocked` rel(tickets) req casc; `owner`; `household`; `created`, `updated` | UNIQUE (`blocker`, `blocked`) |
| `ticket_counters` | `key` text req; `value` number (ganzzahlig, min 0); **keine** autodate-Felder (Pflege per Raw-SQL) | UNIQUE (`key`) |

**Enums (exakt CLAUDE.md):** Status `backlog`, `open`, `in_progress`, `waiting`, `done`, mit den Kategorien backlog/open → offen, in_progress/waiting → aktiv, done → abgeschlossen. Priorität `low`, `medium`, `high`, `urgent`.

**Scope und Key (exakt CLAUDE.md):** `scope` = `h:<householdId>`, wenn `household` gesetzt ist, sonst `u:<ownerId>`. Key = `<CODE>-<NR>` mit Projekt, sonst `TASK-<NR>`. Zählerschlüssel `<scope>:<projectId|TASK>`. Bei Wechsel von Projekt oder Scope bekommt das Ticket einen neuen Key im Ziel-Nummernkreis; der alte Key bleibt in der Historie.

**API-Regeln (exakt CLAUDE.md, für alle fachlichen Collections):**

- list/view/update/delete: `owner = @request.auth.id || (household != "" && @collection.household_members.household ?= household && @collection.household_members.user ?= @request.auth.id)`
- create: `@request.auth.id != "" && @request.body.owner = @request.auth.id`
- `ticket_counters`: alle Regeln `null`.
- Ergänzungen und die Regeln für `users`, `households`, `household_members`, `comments`, `ticket_history` und `dependencies` stehen in OF-2 bis OF-5.

### Paket 4 – API-Regeln mit Negativtests

- **Dateien:** `app/pb_migrations/<ts>_api_rules.js` setzt die Regeln aller fachlichen Collections exakt nach CLAUDE.md, dazu die nach Freigabe übernommenen Ergänzungen aus OF-2 bis OF-5. Tests: `tests/integration/rules.test.mjs`, `tests/integration/realtime-rules.test.mjs`.
- **Akzeptanzkriterien:**
  - Nutzer A sieht und ändert nur eigene Datensätze.
  - Nutzer B bekommt für A-Datensätze bei list eine leere Liste, bei view/update/delete 404, und über Realtime kommen keine Events an.
  - Anlage mit `owner` ≠ eigene ID wird abgelehnt.
  - Anonyme Anfragen werden überall abgelehnt; `POST /api/collections/users/records` ist ohne Superuser verboten.
  - `ticket_counters` ist per API nicht erreichbar, auch nicht für den Owner.
  - Haushalts-Join: Nutzer B ist Mitglied des Haushalts H2 (Datensätze direkt per Superuser angelegt), ein Datensatz von A liegt in H1 → B sieht ihn **nicht**. Ist B Mitglied von H1 → B sieht ihn. Beide Fälle werden getestet, weil sie die Join-Semantik von `@collection` belegen (CLAUDE.md §5).
- **Tests:** wie oben, je Collection und je Operation. Die Realtime-Tests laufen mit dem SDK unter Node (EventSource-Polyfill nur falls nötig, OF-13).

### Paket 5 – Hook: Scope und atomare Key-Vergabe

- **Dateien:** `app/pb_hooks/tickets.pb.js` (Create und Update für Scope, Key), `app/pb_hooks/projects.pb.js` (Scope; Code-Validierung einschließlich reserviertem `TASK`, OF-14), `app/pb_hooks/tags.pb.js` (Scope bei Create und Update, OF-8), `app/pb_hooks/lib/counters.js` (dünner Wrapper für das SQL), `tests/integration/ticket-keys.test.mjs`.
- **Vorgehen:**
  - Zuerst einen Mini-Spike (verworfen, nicht committet) im Wegwerf-Ordner. Er klärt: (a) `e.app.runInTransaction` mit `e.app = txApp` im `onRecordCreate`, (b) `e.app.db().newQuery(sql).bind({...}).one(new DynamicModel({ value: 0 }))` mit `RETURNING`, (c) das Rollback-Verhalten bei einem Fehler nach dem Zähler-Update.
  - SQL (Vorschlag, OF-1): `INSERT INTO ticket_counters (id, key, value) VALUES ({:id}, {:key}, 1) ON CONFLICT(key) DO UPDATE SET value = value + 1 RETURNING value`. Die `id` kommt aus `$security.randomStringWithAlphabet(15, "abcdefghijklmnopqrstuvwxyz0123456789")`.
  - Kollision leerer Werte: Solange `scope` bzw. `key` leer sind, kollidieren sie in den Unique-Indizes `tickets(scope, key)`, `projects(scope, code)` und `tags(scope, name)`. Paket 5 löst das: Die Hooks setzen die Werte immer, dazu je nach Spike-Ergebnis Pflichtfelder oder partielle Indizes (`WHERE scope != ''`). Bis dahin setzen die Regeltests aus Paket 4 `scope`, `key`, `number` und `code` selbst mit eindeutigen Werten.
  - Create: Scope setzen, Key vergeben (clientseitige Werte für `number`, `key`, `scope` werden überschrieben). Update: bei geändertem `project` oder `household` neuer Scope und neuer Key; bei unverändertem Projekt und Scope bleiben `number` und `key` unverändert, auch wenn der Client etwas anderes sendet.
- **Akzeptanzkriterien:**
  - Das erste Ticket ohne Projekt bekommt `TASK-1`, mit Projekt `ABC` bekommt es `ABC-1`. Die Nummernkreise sind getrennt.
  - 25 parallele Anlagen ergeben 25 verschiedene, lückenlose Keys 1…25.
  - Eine fehlschlagende Anlage (zum Beispiel ohne `title`) erhöht den Zähler nicht.
  - Ein Projektwechsel vergibt einen neuen Key im Ziel-Kreis und protokolliert den alten Key in der Historie (sobald Paket 6 umgesetzt ist; der Test wird dort ergänzt).
  - Projekt-Code `TASK` wird abgelehnt, ein doppelter Code im selben Scope ebenfalls.
  - `tags` bekommen ihren Scope vom Hook; ein gleichnamiger Tag (ohne Groß-/Kleinschreibung) im selben Scope wird abgelehnt, in einem anderen Scope zugelassen.
  - Ein Projekt eines anderen Scopes lässt sich nicht zuweisen (OF-3).
- **Tests:** wie oben, zusätzlich ein Unit-Test für `counters.js`, soweit ohne `$app` möglich.

### Paket 6 – Hooks: `completed_at`, Historie, Integritäts-Guards

- **Dateien:** `app/pb_hooks/tickets.pb.js` (erweitert), `app/pb_hooks/comments.pb.js`, `tests/integration/ticket-lifecycle.test.mjs`, `tests/integration/ticket-history.test.mjs`, `tests/integration/ticket-guards.test.mjs`.
- **Inhalt:**
  - `completed_at`: Wechsel nach `done` setzt den aktuellen UTC-Zeitpunkt, das Verlassen von `done` leert das Feld. Clientwerte für `completed_at` werden ignoriert.
  - Historie: Anlage als Eintrag `field = "created"`. Updates vergleichen `e.record.original()` über die Whitelist aus `lib/history.js` und schreiben einen Eintrag pro geändertem Feld in derselben Transaktion wie die Änderung. Den Akteur beschafft Variante A aus OF-4.
  - Guards: `parent` maximal eine Ebene (das Parent hat selbst kein Parent, und ein Ticket mit Kindern bekommt kein Parent), nicht auf sich selbst, gleicher Scope. `project`, `tags` und `recurrence` müssen zum selben Scope gehören (OF-3). `due` muss dem Format `YYYY-MM-DD 00:00:00.000Z` entsprechen. Standardwerte beim Anlegen: `status`, `priority`, `blocks_parent` (OF-11).
  - `comments`: Beim Anlegen muss `author` dem angemeldeten Nutzer entsprechen (Regel, OF-5).
  - `ticket_history` und `ticket_counters` sind über die API nicht beschreibbar.
- **Akzeptanzkriterien:**
  - Die oben genannten Regeln sind erfüllt.
  - Schlägt der Historien-Eintrag fehl, wird auch die Ticketänderung zurückgerollt (Test über einen erzwungenen Fehler, zum Beispiel einen Test-Hook in einer eigenen Hook-Datei, die nur im Harness über ein zusätzliches Hook-Verzeichnis geladen wird; OF-15).
  - Keine Historien-Einträge für unveränderte Felder.
- **Tests:** wie oben, zusätzlich die Ergänzung zu Paket 5 (Projektwechsel mit protokolliertem Alt-Key).

## 5. Offene Fragen (mit Vorschlag)

**OF-1 Transaktionen und Zähler-Anlage.** CLAUDE.md §3/§5 geht davon aus, dass `onRecordCreate`/`onRecordUpdate` in einer DB-Transaktion laufen, und nennt für den Zähler nur `UPDATE … SET value = value + 1 … RETURNING`. In 0.40.4 laufen Record-Create und -Update über die API jedoch nicht in einer Transaktion (Quelltext, siehe Abschnitt 2), und ein reines `UPDATE` legt fehlende Zählerzeilen nicht an. *Vorschlag:* Der Ticket-Hook öffnet selbst `e.app.runInTransaction` (verschachtelt sicher, falls schon eine Transaktion läuft) und vergibt den Zähler per `INSERT … ON CONFLICT(key) DO UPDATE SET value = value + 1 RETURNING value`. Der Spike in Paket 5 bestätigt das Verhalten; danach wird CLAUDE.md entsprechend präzisiert.

**OF-2 Regeln für `users`, `households`, `household_members`.** CLAUDE.md nennt nur „Selbstregistrierung gesperrt“. *Vorschlag:* `users`: list/view/update `id = @request.auth.id`, create/delete `null`. `households`: list/view `@collection.household_members.household ?= id && @collection.household_members.user ?= @request.auth.id`, create/update/delete `null`, bis die Haushaltsstufe freigegeben ist. `household_members`: list/view `user = @request.auth.id`, Schreiben `null`. Später für Haushalte nur Regeländerungen, keine Datenmigration.

**OF-3 Lücken in den fachlichen Regeln.** Die create-Regel aus CLAUDE.md prüft weder die Haushaltsmitgliedschaft beim Setzen von `household`, noch verhindert die update-Regel, dass `owner` geändert oder ein fremder Haushalt eingetragen wird. Relationen (`project`, `tags`, `parent`, `recurrence`) könnten auf fremde Datensätze zeigen, sodass etwa der Code eines fremden Projekts im Key landet. *Vorschlag:* (a) create zusätzlich `&& (@request.body.household:isset = false || @request.body.household = "" || (@collection.household_members.household ?= @request.body.household && @collection.household_members.user ?= @request.auth.id))`; (b) update zusätzlich `&& (@request.body.owner:isset = false || @request.body.owner = owner)` und dieselbe Haushaltsprüfung; (c) der Hook prüft, dass alle referenzierten Datensätze denselben Scope haben. Im MVP wirkungsneutral, schließt aber die Lücke, bevor Mehrnutzerbetrieb möglich wird (ADR-0001).

**OF-4 Akteur in der Historie.** `ticket_history.user` verlangt den handelnden Nutzer, aber Model-Hooks (`onRecordUpdate`) haben laut Doku keinen Zugriff auf Request und Auth. *Vorschlag A (bevorzugt, keine Schemaänderung):* `onRecordCreateRequest`/`onRecordUpdateRequest` hängt die Auth-ID als transienten, nicht persistierten Wert an den Record (`e.record.set("@actor", e.auth.id)`; `Record.Set` speichert unbekannte Schlüssel roh, `record_model.go`). Der Model-Hook liest ihn aus. Fehlt der Wert (System- oder Cron-Änderung), bleibt `user` leer. Der Spike prüft, dass der Wert weder gespeichert noch ausgeliefert wird. *Variante B (Fallback):* persistentes Feld `updated_by` auf `tickets`; das erweitert das Datenmodell und braucht Freigabe.

**OF-5 `comments` und `ticket_history` ohne `owner`.** CLAUDE.md sagt „Alle fachlichen Datensätze tragen owner und household“, listet für `comments` (author) und `ticket_history` (user) aber kein `owner`. *Vorschlag:* kein `owner`/`household` auf diesen beiden Collections; die Sichtbarkeit folgt dem Ticket über die Relation. `comments` list/view: `ticket.owner = @request.auth.id || (ticket.household != "" && @collection.household_members.household ?= ticket.household && @collection.household_members.user ?= @request.auth.id)`. create: gleiche Sichtbarkeit auf das Ticket plus `@request.body.author = @request.auth.id`. update/delete: nur `author = @request.auth.id`. `ticket_history`: list/view wie `comments`, create/update/delete `null` (schreibt nur der Hook). `dependencies` hat laut Tabelle kein explizites `owner`, fällt aber unter „fachlich“, deshalb `owner`/`household` wie in Abschnitt 3. Schreiben bleibt `null`, bis Stufe 2 mit Zyklenprüfung freigegeben ist.

**OF-6 Kaskaden beim Löschen.** CLAUDE.md legt kein Löschverhalten fest. *Vorschlag:* `owner` ohne Kaskade (ein Nutzer mit Daten lässt sich nicht löschen, das schützt vor Datenverlust). `comments`, `ticket_history` und `dependencies` kaskadieren mit dem Ticket. `parent`, `project`, `recurrence` ohne Kaskade. Beim Löschen eines Projekts mit Tickets würde PocketBase die Relation leeren und damit Keys neu vergeben; deshalb verhindert der Projekt-Hook das Löschen, solange Tickets existieren („Projekt archivieren statt löschen“). Tags: Beim Löschen entfernt PocketBase die ID aus `tickets.tags`, und das wird als Änderung protokolliert.

**OF-7 Rollen in `household_members`.** CLAUDE.md nennt nur das Feld `role`. *Vorschlag:* Select `owner` | `member`. Bedeutung und Rechte werden erst in der Haushaltsstufe festgelegt.

**OF-8 Eindeutigkeit von Tags.** CLAUDE.md sagt „eindeutig pro Owner“. Für Haushalte führt das zu gleichnamigen Tags verschiedener Mitglieder im selben Scope. Ein späterer Wechsel auf Scope-Eindeutigkeit würde ein nachträglich befülltes `scope`-Feld verlangen, also eine Datenmigration, was ADR-0001 ausschließt. *Vorschlag:* `tags` bekommt wie `projects` ein vom Hook gesetztes `scope`, eindeutig über (`scope`, `name` COLLATE NOCASE). Im Privatbetrieb ist das gleichbedeutend mit „eindeutig pro Owner“ (ohne Groß-/Kleinschreibung).

**OF-9 Regelparameter von `recurrence_rules`.** „Regelparameter“ ist nicht spezifiziert. *Vorschlag:* In E1 nur die in CLAUDE.md genannten Felder anlegen (für die Relation `tickets.recurrence`). Die Parameterfelder (etwa `freq`, `interval`, `weekdays`, `month_day`, `month_last_day`) kommen in E4 per additiver Migration; zu diesem Zeitpunkt existieren noch keine Regeln, also ist keine Datenmigration nötig.

**OF-10 Feldtypen für Markdown und Längen.** Der PocketBase-Feldtyp `editor` speichert HTML, und `text` hat ohne `max` ein Standardlimit von 5000 Zeichen. *Vorschlag:* `description` als `text` mit `max 100000`, `body` als `text` mit `max 20000`, `title` `max 200`, `name` `max 100` (Tags `max 50`).

**OF-11 Standardwerte.** PocketBase-Selects und -Bools haben keine Standardwerte; `blocks_parent` soll aber „Standard true“ sein, und für `status`/`priority` fehlt ein Standard. *Vorschlag:* Der Create-Hook setzt `status = open` und `priority = medium`, falls leer, und `blocks_parent = true`, sofern der Client das Feld nicht ausdrücklich sendet (Prüfung im Request-Hook über den Request-Body). Alternative für `status`: `backlog`, falls Schnellerfassungen zunächst ungesichtet landen sollen.

**OF-12 Umfang der Historie.** Die Whitelist fachlicher Felder ist nicht festgelegt. *Vorschlag:* wie in Paket 2, also ohne `completed_at` (ergibt sich aus `status`), `number` (steckt in `key`), `scope` (ergibt sich aus `household`) und `owner` (unveränderlich laut OF-3). Werte roh speichern (IDs, Mehrfachwerte als sortiertes JSON-Array); die Anzeige löst die IDs in E2 auf.

**OF-13 Test-Abhängigkeiten.** Für API- und Realtime-Tests unter Node wird das `pocketbase`-SDK im Root als devDependency gebraucht. Node 24 bringt `fetch` mit; ob das SDK für Realtime unter Node ein `EventSource`-Polyfill braucht, klärt Paket 4. *Vorschlag:* `pocketbase` (gleiche Version wie in `web/`) als Root-devDependency; ein Polyfill nur, wenn nötig, mit Begründung im Commit.

**OF-14 Reservierter Projekt-Code `TASK`.** Ein Projekt mit Code `TASK` würde Keys erzeugen, die mit dem projektlosen Nummernkreis kollidieren (`TASK-1` zweimal im selben Scope → der Unique-Index schlägt fehl). *Vorschlag:* `TASK` als Code ablehnen (Hook-Validierung mit deutscher Fehlermeldung).

**OF-15 Fehlerinjektion für Rollback-Tests.** Um „Historie schlägt fehl → Änderung zurückgerollt“ zu testen, braucht es einen erzwungenen Fehler. *Vorschlag:* Das Harness kopiert `app/pb_hooks` und eine zusätzliche Test-Hook-Datei aus `tests/fixtures/pb_hooks/` in einen Temp-Hook-Ordner. Produktivcode bleibt frei von Test-Schaltern.

**OF-16 Frontend-Tests.** Für `web/` ist noch kein Test-Runner eingerichtet. Komponententests brauchen zusätzliche devDependencies (Vitest-Projekt für `web`, `@testing-library/svelte`, `jsdom`). *Vorschlag:* genau diese drei aufnehmen; `npm test` im Root führt die `web`-Tests mit aus.

**OF-17 Abweichungen der E0-Startskripte von CLAUDE.md §9.** `start.bat` wartet fest vier Sekunden, statt `/api/health` abzufragen. Die Portprüfung per `netstat | findstr "127.0.0.1:8090"` trifft auch fremde Verbindungen. `stop.bat` beendet am Ende per `taskkill /IM pocketbase.exe /F` **alle** PocketBase-Prozesse (auch Test-Instanzen) und nutzt das veraltete `wmic`. *Vorschlag:* In Paket 8 `start.bat` korrigieren (Health-Polling, präzise Portprüfung). `stop.bat` in einem eigenen `fix:`-Commit nur den Prozess mit passendem Pfad beenden lassen (PowerShell `Get-CimInstance Win32_Process`); ob das in E1 oder E5 passiert, entscheidet der Nutzer.

**OF-18 Token-Laufzeit.** Die Standard-Laufzeit des Auth-Tokens für `users` beträgt in PocketBase 0.40.4 5 Tage (432000 s, bestätigt in Paket 3). Für eine lokale Einzelnutzer-App ist das eher kurz, `authRefresh` beim Start verlängert aber automatisch. *Vorschlag:* Standard belassen; nur bei spürbar häufigen Neuanmeldungen per Migration verlängern.

**OF-19 Hinweise in bestehenden Dokumenten.** `docs/spikes/e0-pocketbase.md` beschreibt `--automigrate=false` als „Migrations nur aus Dateien, nicht automatisch“. Tatsächlich steuert das Flag nur das automatische *Erzeugen* von Migrationsdateien bei Änderungen im Admin-UI (`plugins/migratecmd`); ausstehende Migrationen wendet `serve` trotzdem an. Außerdem sind in der README E0 noch nicht abgehakt und das Status-Badge steht auf „E0 Scaffolding“. *Vorschlag:* in Paket 9 korrigieren (Spike-Dokument per Nachtrag, nicht durch Umschreiben).

**OF-20 Vorhandenes `app/pb_data`.** Im Arbeitsverzeichnis liegt ein `app/pb_data` aus E0 (gitignored), dessen Superuser-Stand unbekannt ist. Agenten starten dort ohnehin kein `serve`. *Vorschlag:* Der Nutzer entscheidet, ob der Ordner vor dem ersten echten Start gelöscht wird; dann erlebt er den regulären Erststart nach ADR-0002.

## 7. Hinweise für E2

- **Abgelaufene Tokens:** In lange offenen Tabs kann der Token (5 Tage, OF-18) ablaufen. Die Listenregeln liefern dann für den nicht mehr angemeldeten Client leere Listen statt 401, der Fehler fällt also nicht auf. Den Token vor dem Ablauf erneuern (`authRefresh`) bzw. vor Anfragen `pb.authStore.isValid` prüfen und sonst zum Login leiten.
- **Logout:** Beim Abmelden alle Realtime-Abos beenden (`pb.realtime.unsubscribe()`), sonst laufen sie ohne Berechtigung weiter bzw. werden nach erneuter Anmeldung doppelt.
- **Veraltete Anfragen:** Die Auto-Cancellation des SDK ist global aus (Paket 7). Filter- und Suchlisten verwerfen veraltete Anfragen deshalb selbst per `AbortController` (`signal` in den Request-Optionen).
- **Kopfzeile:** Für die Kopfzeile (App-Name, „Angemeldet als …“, „Abmelden“) ein gemeinsames Gruppen-Layout (`(app)/+layout.svelte`) anlegen, statt sie pro Seite zu wiederholen.
- **Fehlerfarbe:** Ein eigenes Fehlerfarb-Token ist eine Design-Entscheidung nach CLAUDE.md §8 (Petrol ist die einzige Akzentfarbe) und braucht Rücksprache; bis dahin gilt die Lösung aus Paket 7.
- **Login-Fehlermeldungen:** Beim Login bekommen 5xx und 429 derzeit die generische Ablehnungsmeldung. Prüfen, ob in E2 eine eigene Meldung für Serverfehler bzw. zu viele Versuche sinnvoll ist (ohne preiszugeben, ob die E-Mail existiert).
